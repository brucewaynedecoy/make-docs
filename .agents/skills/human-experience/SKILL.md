# Human Experience

Help the affected person understand what matters and complete their goal with little needless thought, effort, or doubt. Treat pleasant use as part of the work. Preserve truth, control, and the agreed product behavior.

## Fit the request

Apply this skill to the assigned surface: chat, decisions, documents, directories, commands, configuration, interfaces, or handoffs. “Review” means inspect and report. “Improve,” “write,” or “build” permits the requested edits. Do not broaden a review into a redesign.

Find the person, goal, and promised result from the request and accepted sources. Ask only if missing context would change the work. Follow existing Make Docs human experience requirements where applicable. Do not create a competing standard or require new lifecycle documents.

## Shape the result

- Start with the person's task. Use names they can recognize. Explain a needed special term where it first matters.
- Show what happened, what changed, and how important things relate. A successful operation is not enough if the relationship stays hidden.
- Keep context visible as the person moves through a task. Make the next useful action clear.
- Put detail where it helps. Keep precise machine output available without making people join IDs or read raw JSON to understand ordinary results.
- Show material limits and failures at the useful point. Make recovery and control clear.
- Use a coherent structure, accessible presentation, and calm language. Shorter output or extra decoration alone does not prove a better experience.

Read [surface examples](references/surfaces.md) only when they help the current work. For internal work, consider maintenance, recovery, reliability, and cost. Do not invent an interface or an experience essay for a change with no relevant human effect.

## Check the actual experience

Inspect the real document, normal command output, file structure, or interaction. Use the smallest check that answers the goal. Reuse suitable evidence. Do not give a passing verdict merely because implementation tests pass.

For a review, report each material finding as: the person's goal, what you observed, its effect, and a bounded improvement. For edits, check the changed result against the same goal. When a change would alter settled behavior, present that departure before making it.

State the basis and limit of your conclusion. “The output now names the person beside the alias” is evidence. “Humans find this delightful” requires human judgment. Do not claim lived ease or pleasure from an agent review. Use a qualified human when the project requires one.

Keep the closeout short: outcome, evidence, and any material next step. Do not create state files, test ledgers, or extra approval gates. Do not activate another skill merely because its subject is related.
