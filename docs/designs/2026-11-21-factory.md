# Factory

## Purpose

Make Docs plans the work, and its factory runs the work. This design defines the factory: an opt-in area of Make Docs that sets up a person's agent tools once, saves that wiring, and then lets agents take ready work, do it, review it, correct it, and bring results and decisions back to the person.

The factory has no workflow engine. The person's own tools do the work. Make Docs teaches agents how to use those tools, saves the setup and the assignment records, and supplies the work queue through the [work store](2026-11-21-work-store.md).

## Context

Make Docs already ships a `factory` Skill in `packages/skills/factory/`. It runs a small loop: select ready work, send a bounded brief to a worker, judge the actual result, return defects, and integrate. It is explicit-invocation-only ([PRD 08 R-SKILL-BUNDLE-3](../prd/08-skills-catalog-and-distribution.md), [PRD 25 R-SKILL-RUNTIME-2 and -4](../prd/25-typescript-runtime-cli-mcp-operation-boundaries.md)). It defaults to native subagents. It forbids a tracker, a private state schema, and a workflow engine, and it limits saved progress to one lifecycle checkpoint of 256 characters. The owner reports that it was rarely used, because it did not work well in practice. It had no saved setup, no shared work queue, no way to wake on its own, no way to reach the person away from the session, and no record of which tool was doing which work.

The owner settled these points in two grill sessions on 2026-11-21:

- The factory is tool-agnostic. It is a product for any user. It must not assume that any particular app, harness, provider, or multiplexer is present.
- It is built inside Make Docs and stays there. It uses the Store, config, system resources, the CLI, and the MCP server. It grows the existing `factory` Skill.
- Workflow types ship as system resources. One run Skill loads the chosen type and the config. Projects can add their own types.
- The Store holds the durable record of each factory setup and each assignment. Files in `.make-docs/factory/` are copies that Make Docs writes from the Store. Portable choices go in the committed project config. Machine IDs and paths stay in the Store.
- Each workflow saves one human channel. The last resort is "wait in session".
- Setup proves the wiring with one small test task before it marks a workflow ready.
- The factory is opt-in. It stays off until a person runs factory setup.
- v1 covers software, personal, and business work. Software work comes first.

On 2026-11-23, after W30 R0 P1 was done, the owner reviewed this design again and approved five changes. All five are new behavior that no earlier version of this design had:

1. A fixed table of assignment status moves with final states, and a correction round count that the CLI enforces.
2. Capability proofs that record the tool version, a three-way result, and a "does not cover" list, and a setup summary that lists each accepted known loss.
3. A never-log list for factory records, and stable reason codes.
4. Grants with a scope and an optional expiry.
5. A resolved workflow plan: one generated record that joins the three workflow sources, saved as immutable revisions.

Later on 2026-11-23, the owner chose option A for project scope. Every factory write names its project. It never falls back to the current folder. Machine-level commands take no project. Every result names what it acted on. Factory URIs live under the project URI. This is new behavior too. No earlier version of this design said how a factory command finds its project. See [Project scope](#project-scope). Later the same day, the owner answered seven more W30 choices. All seven are new behavior:

1. `factory status` shows one project, with one group for each running factory, and each assignment records its checkout (register D-073, closed).
2. The factory URI paths are approved (register D-074, closed).
3. The four project refusal codes stay, and URI reads show saved records only. The folder grant rule covers factory URI reads only. Factory MCP tools keep the normal grant and target check.
4. A `.gitignore` file inside each factory folder keeps it out of git. Make Docs never edits the project root `.gitignore`.
5. The integration owner role and the human channel kind live only in config.
6. A move from `unknown` to `needs-correction` counts a correction round. One exception follows below.
7. A role other than builder or reviewer must list its context kinds. This was narrowed below to custom roles only.

The owner then settled three items that stayed open, all option A and all new behavior:

- A move from `unknown` to `needs-correction` adds no round when the status before `unknown` was already `needs-correction`.
- Only a custom role must list its context kinds. The front desk and the foreman need no list.
- A factory MCP tool call for another project needs that project's own grant (register D-075, closed).

Relevant facts from the code at `ba4b95b5`:

- Lifecycle runs have stages `design`, `plan`, `prd`, `work`, `implementation`, `release`, `archive`, and `retrospective`. They have no assignee, tool, or task handle field.
- `evidence_record` saves one evidence row per project, wave, phase, and kind.
- Skills are off by default. The factory Skill is installed only when a person selects it.
- `.make-docs/config.yaml` has no `factory` key today. The validator rejects unknown top-level keys.
- The Store keeps no config content and no file bodies. [PRD 38 R-DB-5](../prd/38-global-store-and-project-state.md) forbids a project-local copy of receipts. The factory copies therefore need a new, narrow rule.
- System resources have four types: contract, prompt, reference, and template. Playbooks and Protocols are not current capabilities and must not return.

## Human Experience Intent

Impact: `direct`

Affected humans: the person who directs agent work in a project (the `user` Persona when they use Make Docs, the `maintainer` Persona when they maintain the setup), and teammates who share the project.

Human goal or effect: Hand ready work to agents, leave, and come back to results, evidence, and only the decisions that need a person.

Experience promises:

- Setup ends with a plain summary: which tool fills each role, how the workflow wakes, how the factory reaches the person, what the test task proved, each known loss that the person accepted, and each manual step that is still open.
- When a tool changes version, or the setup changes without a save, the factory says what changed in plain words, with its reason code, before it takes new work.
- During a run, the person hears only the events on the escalation floor and the events they added. Each message says what happened, what the factory needs, and what happens after the person answers.
- `make-docs factory status` shows one project, with one group for each running factory: by checkout, then by lifecycle run. It shows each claimed unit, the tool working on it, its state, and the last time the factory checked it, in human words first.
- At the end of the scope the person gave, the person gets one acceptance request with the reviewed result and its evidence.
- A workflow that has lost a tool or a permission says so before it takes new work. It names the smallest step to fix it.
- New on 2026-11-23: every factory result names the project it acted on, or says that it acted on this machine. A write that names no project changes nothing and says how to name one.

Complexity kept out of the human path:

- The person does not need to know tool names, adapters, task handles, or Store tables to set up or use a workflow. Setup finds the tools and asks only for preferences and permissions.
- The person does not restart the run after each unit. Worker completion returns control to the foreman.
- The person does not read transcripts to judge work. The foreman judges the actual result, and the reviewer checks it.

Evidence required:

- Two first-release proofs, described by capability: the smallest setup (one harness, its own subagents, "wait in session"), and a multi-tool setup (a multiplexer plus a human channel that the person can use from a phone). The release notes name the real tools used.
- A review of the setup summary, status output, escalation messages, and the acceptance request against the promises above.
- A drift test that removes a wired tool and shows the blocked state and the fix step before new work starts.
- A test in a folder without git that shows the file backup, its cleanup, and the backup folder note.

## Decision

### Parts

| Part | What it is | Who owns it |
| --- | --- | --- |
| `factory-setup` Skill | Teaches any agent to find tools, read their instructions, interview the person, wire the workflow, run the test task, and save the result. | New first-party Skill in `packages/skills/factory-setup/`. Explicit invocation only. |
| `factory` Skill | The run Skill. Loads one saved workflow and its type, then runs the loop. | The existing Skill in `packages/skills/factory/`, rewritten. Explicit invocation only. |
| Workflow types | Reference resources such as `make-docs://system/reference/factory/workflows/build-then-review.md`. | Authored upstream in `packages/docs/template/`. No new resource type. |
| Factory rules | `make-docs://system/contract/factory-contract.md`: roles, escalation floor, acceptance, working rules, and the agent form of the shared rules. | Authored upstream in `packages/docs/template/`. |
| CLI and MCP | Check and save setup, workflows, assignments, proofs, and backups. Write the `.make-docs/factory/` copies. | `packages/cli/`. Never launches an agent. |
| Store tables | Machine tools, workflow bindings, grants, assignments, proofs, and backups. | PRD 38, schema v9 or later, after the W29 work store's v8. Each table has the Store write guard triggers. |
| Work queue | `work next`, `claim`, `report`, and `close`. | The [work store](2026-11-21-work-store.md). |

The CLI never dispatches, schedules, or messages anything. It checks and records. An agent does the work through the tools that setup wired.

### Minimum and growth

The smallest setup is one agent tool that can read files, write files, and run commands. In that setup, one agent is the front desk and the foreman. Builders and reviewers are fresh subagents of that agent. The reviewer is never the session that built the work. When more tools are present, setup uses them.

The factory needs the CLI and a usable Store, because setup and assignments live in the Store. Without them, `factory-setup` stops, says which one is missing, and names the setup step. The factory has no zero-config mode.

### Roles

The factory ships four standard roles. Projects can add their own.

| Role | Job |
| --- | --- |
| Front desk | Talks to the person through the workflow's human channel. Turns a request into a work unit, or a quick item, and passes it to the foreman. |
| Foreman | Syncs the work store, checks open assignments, takes ready work, chooses the team for each unit, assigns jobs, judges results, accepts units inside the given scope, and escalates. |
| Builder | Does one bounded job and returns the actual result and its evidence. |
| Reviewer | Checks a candidate against the requirements. Never reviews its own work. |

A custom role names its job, the capabilities it needs, what it returns, and its context kinds, for example a researcher, an analyst, or a writer. New on 2026-11-23: only a custom role must list its context kinds. The front desk and the foreman need no list, and the builder and the reviewer keep their default lists. The config check refuses a custom role without a list, with a plain message that names the role, for example: `The role "researcher" has no context list. A custom role must list its context kinds, for example [unit-record, requirements].`

### Matching tools by capability

Setup gives a role to a tool because of what the tool can do, not because of its name. The capability list includes, at least: read and write files, run commands, launch agents, wait for an agent to finish, read an agent's result, wake on a schedule, wake on an event, message the person, receive the person's answer, isolate a working copy, and edit code. Setup records the capabilities it found, how it proved each one, and the role it gave each tool. A capability that a tool's docs claim but setup could not prove stays marked as unproved.

New on 2026-11-23: each proof records the tool version that the agent reported, the proof time, a result of `proved`, `unproved`, or `contradicted`, and a "does not cover" list. `contradicted` means that setup ran the proof and the tool failed it. A proof holds only for the version it names. When an agent reports a new version of a bound tool, the workflow is `drifted`. To reach `ready` again, setup proves that tool again and saves the proofs, saves the workflow (a new plan revision), and passes a new test task. If the old version comes back first, the plan matches the `ready` revision again, and the workflow is `ready` with no new step. The CLI compares the versions that agents report. It never asks a tool. Setup names each known loss (a capability that no tool could prove, a "does not cover" item, or no way to wake on its own), asks the person to accept it, and lists each accepted loss in the summary. Capability IDs are lower-case, only added, and never given a new meaning.

### Setup

The `factory-setup` Skill runs these steps:

1. Find the agent tools on the machine and in the project: harnesses, providers, multiplexers, MCP servers, schedulers, and messaging tools.
2. Read the instructions that those tools make available: their help, docs, MCP tool lists, and Skills.
3. Interview the person for preferences: the workflow type, the human channel, the wake method, the limits, and the permissions to grant.
4. Wire roles to tools by capability.
5. Run one small test task through the whole workflow, from intake to return.
6. Save the result as config and Store records, and write the `.make-docs/factory/` copies.

A workflow has a readiness state: `draft`, `wired`, `ready` (after a passed test task), or `drifted` (a wired tool or permission is gone). Only a `ready` workflow takes new work. Since 2026-11-23, the CLI finds the state from resolved plan digests (see [Resolved workflow plan](#resolved-workflow-plan)). A one-time manual step, such as a sign-in or an app permission, is allowed. Setup lists each one with what the person must do and what it unblocks. The tool list for each machine is saved once in the Store and reused by every project on that machine. Each project saves only its own workflow choices.

### Saved records

| Record | Where | Why |
| --- | --- | --- |
| Workflow choices: type, roles needed, capability needs, limits, steps such as preflight, and added escalation events | `factory:` block in `.make-docs/config.yaml` | Portable. Teammates and other machines can rebuild the same workflow. |
| Machine tools, capability proofs, and role bindings | Store | Machine-specific. Holds paths and IDs. |
| Grants: merge, deploy, publish, spend, or other actions outside the default authority, each with a scope and an optional expiry | Store | A grant is one person's permission on one machine. It is not committed. |
| Human channel binding (the account reference) and wake binding | Store | Machine- and account-specific. The human channel kind and the integration owner role stay in config only. |
| Resolved plan revisions | Store | The exact plan that each assignment runs under (see below). |
| Assignments | Store | Durable run record (see below). |
| Proof results | Store | The H07 evidence that a workflow is ready. |
| File backups | Store record plus `.make-docs/backup/factory/` | Undo outside git (see below). |

`.make-docs/factory/` holds read-only copies of the saved setup, written only by Make Docs. New on 2026-11-23: a `.gitignore` file inside the folder holds one line, `*`, and keeps the folder out of git. `.make-docs/backup/factory/` gets the same file. Make Docs never edits the project root `.gitignore`. Each file starts with a note that it is generated and that edits are lost. `make-docs factory restore` writes them again. They let an agent or a person read the wiring without a CLI call. They are never an input. The copy of the resolved plan prints the latest revision and says whether it is the `ready` revision. It reads the integration owner role and the human channel kind from the resolved plan. Since 2026-11-23, those two fields live only in config, and the Store binding keeps no copy of them. PRD 38 gains one narrow rule that allows these copies and keeps every other part of R-DB-5. No secret is saved in config, in a copy, or in a Store record. Secrets stay in the tools that own them.

### Grants and their scope

New on 2026-11-23. Each grant records its action, a scope, an optional expiry time, who granted it, and when. The scope is `once` (one use), `run` (one lifecycle run, until it ends), or `standing` (until the person revokes it). Before an action outside the default authority, the foreman records the use of a grant through `factory assignment update`. The CLI refuses a use with no matching grant, outside the scope, after a `once` grant is spent, or after the expiry. The foreman then asks the person again, as floor event 1. `factory workflow save` writes each grant. During a run, after the person answers an escalation, the foreman records the answer with a grant-only save, and a `run` grant names its lifecycle run. A grant-only save writes nothing else. All of this is new behavior. Setup recommends the narrowest scope.

Grants stay out of the resolved plan. `factory workflow show` lists them beside the plan, and no `.make-docs/factory/` copy ever holds a grant. A grant changes what the foreman may do without asking. It does not change the wiring, so a new or spent grant never needs a new test task.

### Never-log list and reason codes

New on 2026-11-23. Factory records never hold file contents, prompts, briefs, environment values, transcripts, or credentials. This covers the `factory:` block, every Store record, every resolved plan, every copy, and every status history entry. The CLI checks every factory write: only defined fields, free text only as one line of at most 120 characters, and no value that looks like a credential or an environment setting. A refusal names the field, never the value. The backup copies outside git are file copies, not records. The same list applies to the progress note of `make-docs work report --note` (one line of at most 256 characters).

Drift results, refusals, and status history entries use reason codes. A code is lower-case kebab-case. It is only ever added, never removed, renamed, or given a new meaning. The contract holds the lists. A message to the person explains each code in plain words.

### Resolved workflow plan

New on 2026-11-23. A workflow keeps its three sources: the portable choices in the `factory:` config entry, the machine binding in the Store, and the workflow type reference. The CLI joins them into one generated record, the resolved plan. It is not a plan under `docs/plans/`.

| Layer | Where | What it holds |
| --- | --- | --- |
| Portable definition | `factory:` entry in `.make-docs/config.yaml` (committed) | Type name and type version. Each role's job, needed capabilities, returns, and context kinds. The round limit. The gates and escalations that only a person decides. The other limits. Preflight on or off. The integration owner. The human channel kind. |
| Machine binding | Store | For each role: the bound tool, the proved tool version, the proof result, and the "does not cover" list. For the workflow: the wake method, the human channel account (a reference, no secret), the working-copy method, and the accepted known losses. |
| Resolved plan | Store, as revisions | Both layers plus the type name, type version, type file digest, and the status move table version, as canonical JSON with a digest. |

The context kinds come from a fixed set: `unit-record`, `requirements`, `project-files`, `candidate-result`, `defect-list`, `evidence-links`, and `builder-summary`. A role sees only what it is handed. By default, a reviewer never gets `builder-summary`, so the brief does not steer it. The plan names the kinds. The content is handed over at run time and never saved.

The status move table is part of the contract and the same for every workflow. The plan records its version, so a later contract change never changes a running assignment. A workflow type states its version as `Type version: N` in its `## Purpose` section. The config names the version the person chose.

The plan record is canonical JSON: sorted keys, no extra spaces, UTF-8. Its digest is the SHA-256 of those bytes. The CLI also records a config digest and a binding digest, so a person can see which layer changed. The Store saves each plan in a new table, `factory_workflow_plans`, with the workflow name, revision number, plan digest, plan JSON, config digest, binding digest, and created time. A saved revision never changes.

| Command | Role |
| --- | --- |
| `make-docs factory workflow save` | Resolves the plan. Saves a new revision only when no kept revision has its digest. Never makes a revision `ready`. A grant-only save writes just the grant. |
| `make-docs factory proof save` | Records the test task for one plan digest. Refuses a digest that is not the current plan or has no saved revision. On a pass, that revision becomes the `ready` revision. |
| `make-docs factory workflow show` | Reads the latest revision, or a named one, with the current digest, the `ready` revision, and drift reason codes. Lists grants beside the plan. Writes nothing. |
| `make-docs factory restore` | Prints the latest (newest saved) revision to `.make-docs/factory/`, with no grant. |

No command name changes, so the W33 command tree and the 26-character MCP name limit hold. The longest factory MCP name stays `factory_assignment_update`.

Retention: the table is in the `bounded` maintenance class. For each workflow, the Store keeps the `ready` revision, each revision that an open assignment names, and the 10 newest other revisions. Each save removes older revisions in the same write.

The CLI computes the current plan each time from three live sources: the config file, the workflow type file, and the machine tool rows in the Store. The tool rows give each bound tool's state (`available`, `missing`, or `blocked`), its reported version, and its proof results. The CLI does not take these facts from the saved binding. The saved binding gives only the choices that setup saved, and they change only through a save. Then the CLI compares digests. The current plan matches the `ready` revision: `ready`. It matches another saved revision: `wired` (or `draft` when a role is unbound). It matches no saved revision: something changed without a save, such as a lost or blocked tool, a new tool version, a config edit by hand, or a changed type file. The workflow is `drifted`, with its reason codes. A fix that restores the exact `ready` plan makes the workflow `ready` again with no new test task, because the passed proof belongs to that digest. An agent records a gone tool as `missing`, and a tool that lost a permission it needs (an app permission or a sign-in) as `blocked`, through `factory tools save`. An expired or spent grant never changes readiness.

Each assignment records the revision number and digest it runs under. `factory assignment start` uses the `ready` revision and refuses when the workflow is not `ready`. A takeover loads the exact revision that each open assignment names.

The resolved plan is data, not a program. It says who does each job, with which tool, under which limits, and which move table version applies. It has no steps, conditions, branches, joins, or code. The CLI checks writes against it. It never reads the plan to choose a next step, and it never starts anything. The foreman still runs the loop from the Skill. So Make Docs still has no workflow engine, and PRD 53 R-FACTORY-5 holds. The plan never holds prompts, file contents, or secrets.

### Assignment record

An assignment links one job to the tool doing it. It holds the work unit, the role, the tool, the tool's task handle (for example a thread ID or a run ID), the lifecycle run ID, the status, and the time of the last check. Status values are `offered`, `running`, `returned`, `in-review`, `needs-correction`, `accepted`, `failed`, `cancelled`, and `unknown`. `unknown` means the factory lost track and must check the handle before any other step. The record holds no prompts, transcripts, or task graphs. The tool keeps those. This replaces the old Skill rule that forbade a tracker and limited saved progress to one 256-character checkpoint. The lifecycle checkpoint limit itself does not change.

New on 2026-11-23: an assignment also holds a part label, the checkout ID of the checkout that `assignment start` named, not a worker's working copy, a correction round count, the revision number and digest of its resolved plan, and a status history of its 20 newest changes. Each history entry holds the status, the time, and one reason code, with no free text. Status moves follow one fixed table:

| From | Allowed next status |
| --- | --- |
| `offered` | `running`, `unknown`, `failed`, `cancelled` |
| `running` | `returned`, `unknown`, `failed`, `cancelled` |
| `returned` | `in-review`, `needs-correction`, `unknown`, `failed`, `cancelled` |
| `in-review` | `accepted`, `needs-correction`, `unknown`, `failed`, `cancelled` |
| `needs-correction` | `offered`, `running`, `unknown`, `failed`, `cancelled` |
| `unknown` | `offered`, `running`, `returned`, `in-review`, `needs-correction`, `failed`, `cancelled` |
| `accepted`, `failed`, `cancelled` | None. These are final and never change. |

The round count starts at 0 and goes up on each move from `returned` or `in-review` to `needs-correction`. Since the owner's choices on 2026-11-23, a move from `unknown` to `needs-correction` also adds one, except when the status before `unknown` was already `needs-correction`, as the status history shows. Then the move adds no round. The CLI refuses a move past the plan's round limit (default 3), and the foreman escalates. A job is one unit, one role, and one part label, such as `research` or `draft`. A unit with one part uses `main`. The count is on the job, so it survives a takeover. Only one assignment for each job is open at a time, so the parts of a lead and specialists unit can still run side by side, each with its own count. A new assignment for the same job starts at the count of the one before it. Only the person can reset it, through a `once` grant for `reset-correction-rounds`. `factory assignment start` spends that grant, and the new assignment starts at 0. `assignment start` and `update` take the private claim ID of the live claim, as the work queue requires.

### Claims and lifecycle runs

The foreman can claim a wave, a phase, a stage, or a task. The default is a phase. When it claims a unit, it opens one lifecycle run at stage `implementation`. Each assignment points to that run. Evidence goes in through `evidence_record` and `lifecycle_attach_evidence`. The foreman renews the work store claim at each check. If a foreman stops and the claim expires, another foreman can take the unit after it checks every open task handle.

A quick item comes straight from a request through the front desk. It is a task-level unit with no design, plan, or PRD. The foreman still routes it by capability, so a small job can still go to a separate agent. Large work goes through the full lifecycle.

### The loop

Each time the foreman wakes:

1. Sync the work store and read the workflow's readiness. If the workflow is `drifted`, escalate and take no new work.
2. Check each open assignment through its task handle. Renew claims. Settle `unknown` assignments first.
3. Judge returned work: inspect the actual result, send it to a reviewer who did not build it, and return defects for correction within the limit.
4. Accept each unit inside the given scope on the reviewer's evidence, close it in the work store, and integrate it.
5. Take the next ready unit if the scope and the limits allow. Run preflight first when the workflow turns that step on. Choose the team and assign the jobs.
6. Escalate each floor event. At the end of the scope, ask the person to accept.

### Waking

The selected tools wake the foreman, not Make Docs. Setup saves how each workflow wakes: a schedule, an event, or a person. If no tool can wake on its own, the workflow runs only while a person keeps a session open, and setup says so.

### Human channel

Each workflow saves one human channel: how the factory sends a message and how the person answers. A channel can be a messaging tool, an agent app that the person follows from a phone, or any other tool that setup proved can send and receive. The last resort is "wait in session": the factory asks in the chat and waits for the person to come back.

### Escalation floor

These events always go to the person. A workflow can add events. It cannot remove these:

1. Any action outside the granted authority, for example a merge, a deploy, a publish, or spending money.
2. A scope change: a change to the outcome, the scope, or the acceptance criteria.
3. A correction loop that stops because it fails the same way again, or reaches its round limit.
4. A missing tool, a missing permission, or wiring that has broken.
5. Work that is ready for the person to accept at the end of the given scope.

### Acceptance

The person accepts at the end of the scope they gave, for example a whole wave. Inside that scope, the foreman accepts each unit on the reviewer's evidence. A merge or a deploy still needs a grant. A Store receipt is never product acceptance.

### Workflow types

v1 ships three types. All three work for software, personal, and business work.

| Type | Shape |
| --- | --- |
| Build then review | One builder does the job. A separate reviewer checks it. The foreman returns defects and repeats within the limit. |
| Lead and specialists | The foreman splits one unit across specialists, for example a researcher, a builder who proves a hypothesis, and a writer, then integrates their results. |
| Staged backlog | The foreman works through ready units in dependency order. Each unit uses one of the other two types. |

A project can add its own type as a committed, project-owned file. The plan fixes its path. A project type uses the same fields as a shipped type and can never replace a shipped type silently.

### Limits

Each workflow saves its limits. The defaults are three correction rounds before the foreman escalates, and no more parallel workers than the wired tools allow. A person can change both at setup.

### Working rules

These rules from the current Skill stay:

- Judge the actual work, not the worker's summary.
- A reviewer never reviews work it built. The brief does not steer the reviewer toward the builder's conclusions.
- Stop a correction loop that repeats the same failure.
- Do not send work again after an unclear handoff. Check its status first.
- Green tests do not prove the right behavior. Do not weaken requirements to make a result pass.

These rules change:

- **One writer per file in each working copy.** Parallel workers in separate worktrees can change the same file. The workflow names one integration owner, who merges the work and settles conflicts.
- **Worktrees.** The factory has no worktree rule of its own. The harness and the repo instructions own that policy. Setup saves each workflow's worktree method. The factory still obeys a repo or user rule that forbids worktrees.
- **Preflight.** A workflow can turn on "run preflight on the unit before claiming it". The person turns it on at setup, so the permission is explicit. Without that step, the factory does not start preflight.
- **Profiles.** Workflow config replaces the Skill's profiles.

### Undo outside git

In a folder without git, the factory copies a file to `.make-docs/backup/factory/` before a worker changes it. The Store records each backup with its file, its hash, and its assignment. Make Docs deletes the backups of an assignment when its work is accepted or closed, and deletes any backup older than 30 days. Cleanup runs during normal factory commands. A `README.md` in the backup folder tells people and agents this rule and how to get a file back.

### Backlog review

When a workflow is `ready`, the backlog review "Work on this wave" button sends the wave to the foreman through the front desk. Without the factory, the button works as it does today.

### Commands and MCP tools

| Command | Effect |
| --- | --- |
| `make-docs factory status` | Reads workflows, readiness, claims, assignments, and open manual steps. |
| `make-docs factory tools save` | Checks and saves the machine's tool list and capability proofs. |
| `make-docs factory workflow save \| show \| list` | Checks and saves one workflow's choices and bindings and a new resolved plan revision when the plan changed, or reads them. |
| `make-docs factory proof save` | Saves a test task result for one plan revision and makes it the `ready` revision when it passed. |
| `make-docs factory assignment start \| update \| list` | Records and reads assignments. Update checks status moves, rounds, and grant use. |
| `make-docs factory restore` | Writes the `.make-docs/factory/` copies again, with the latest resolved plan. |

Each command is also an MCP tool in a new `factory` MCP profile. The plan and PRD fix the exact flags. Writes use the existing write permission, `expectedVersion`, and Store-unavailable rules.

### Project scope

New on 2026-11-23. The owner chose option A. All of this is new behavior.

One Store serves every project on a machine. So each factory command must know what it acts on. An agent often works in one folder while it runs work for a project in another folder. A write that falls back to the current folder can then change the wrong project.

| Command | Scope | Kind | How it finds the project |
| --- | --- | --- | --- |
| `make-docs factory tools save` | Machine | Write | It takes no project. |
| `make-docs factory workflow save` | Project | Write | Named project only. A grant-only save is a project write too. |
| `make-docs factory proof save` | Project | Write | Named project only. |
| `make-docs factory assignment start` | Project | Write | Named project only. |
| `make-docs factory assignment update` | Project | Write | Named project only. |
| `make-docs factory restore` | Project | Write | Named project only. |
| `make-docs factory workflow show` | Project | Read | The named project, or the project of the current folder. |
| `make-docs factory workflow list` | Project | Read | The named project, or the project of the current folder. |
| `make-docs factory assignment list` | Project | Read | The named project, or the project of the current folder. |
| `make-docs factory status` | Project | Read | The named project, or the project of the current folder. See [`factory status` scope](#factory-status-scope). |

The machine records are the tool list, the tool states, and the capability proofs. They belong to the machine, and every project on it uses them. All other factory records belong to one project.

**Writes name their project.** A project write names its project with `--target-root <path>` or with `--project <name>`. In MCP, the inputs are `targetRoot` and `project`. The `--project` option is new. A name resolves only through `project_register`. A write never falls back to the current folder, even when that folder is a project. The CLI refuses a write and changes nothing in these cases:

- No project is named: `project-missing`. The message names both ways to name one.
- The name is not in `project_register`: `project-not-found`.
- `--target-root` and `--project` name two different projects: `project-mismatch`.
- The write must read or write project files, and the named project has no bound checkout or more than one: `project-checkout-unclear`. The message asks for `--target-root`. `workflow save`, `proof save`, and `assignment start` read the config file and the type file to find the current plan. `restore` writes the copies into one checkout.

A `--target-root` path that is not a bound project gets the existing typed Store outcome.

**Results name what they acted on.** Every factory result, in the CLI and in MCP, names the project it acted on, with its project name and project ID. A machine command says that it acted on this machine. A refusal says which project it refused, or that no project was named. The human words come first, for example "Saved workflow `build-then-review` for project `make-docs`."

**Reads show their project.** A read can still use the project of the current folder when no project is named. Its output names the project it read and says how it was chosen: named, or taken from the current folder. A read in a folder that is not a project, with no project named, is refused with `project-missing`.

#### `factory status` scope

Decided on 2026-11-23: the owner chose option A, one project, with one change ([register](../prd/03-open-questions-and-risk-register.md) D-073, closed). All of this is new behavior.

Several factories can run in one project at once, each in its own worktree. So `factory status` shows one project, named or taken from the current folder, and names it. It shows one group for each running factory:

- It groups by checkout, then by lifecycle run.
- Each checkout group shows its own readiness, from that checkout's config file and type file.
- A checkout that has an open assignment gets a group, and so does the checkout that the call named or ran in. A checkout that cannot be read shows its readiness as unknown and says why.
- Each run group shows each claimed unit, its tool, its state, and the last check time.
- `--run <run-id>` shows one lifecycle run. The option is new.

To group by checkout, each assignment records the checkout ID of the checkout that `assignment start` named, not a worker's working copy. `assignment start` already needs exactly one checkout, so it has one to record.

The option that was not chosen showed every project on this machine. That view may come later as a separate option, and it would be new behavior.

#### Factory URIs

Approved on 2026-11-23: the owner chose option A ([register](../prd/03-open-questions-and-risk-register.md) D-074, closed). All of this is new behavior.

Factory URIs follow the W29 project URI rule in [PRD 52](../prd/52-work-store-and-work-queue.md) R-WORK-URI-1. They live under `make-docs://project/<project>/` and name the project in full. `<project>` resolves only through `project_register`. Nothing in a factory URI comes from the current folder, a target path, or a checkout.

| Path | What a read shows |
| --- | --- |
| `make-docs://project/<project>/factory/` | The project's workflows. For each: its latest revision number and its `ready` revision number. |
| `make-docs://project/<project>/factory/workflows/<name>` | The latest saved resolved plan revision of one workflow: its number, its digest, the plan, and whether it is the `ready` revision. |
| `make-docs://project/<project>/factory/workflows/<name>/revisions/` | The kept revisions: number, digest, time, and which one is `ready`. |
| `make-docs://project/<project>/factory/workflows/<name>/revisions/<n>` | One named revision. |
| `make-docs://project/<project>/factory/assignments/` | The project's open assignments: unit, role, part label, tool, status, round count, last check time, plan revision, and lifecycle run ID. |

Examples: `make-docs://project/make-docs/factory/`, `make-docs://project/make-docs/factory/workflows/build-then-review`, and `make-docs://project/make-docs/factory/workflows/build-then-review/revisions/3`.

A project URI names no checkout. So a factory URI read cannot read the config file or the type file, and it cannot find the live readiness state. It shows only the saved records. Each read ends with a note to run `factory status` in a checkout for the live readiness state. This follows the W29 rule for sync conflicts in a backlog URI read.

The first release has no path for one job and no `@<digest>` form. Machine records get no URI. Any other path under `factory/` is refused with `resource-not-found`.

**Access.** An MCP read of a factory URI follows [PRD 25](../prd/25-typescript-runtime-cli-mcp-operation-boundaries.md) R-ACCESS-2. The harness grant of the folder where the agent works decides, never the grant of the project that the URI names. A Store read grant there allows every project URI. A folder that is not a project gets a plain `store-not-configured` refusal, with no setup step for that folder. Since the owner's choice on 2026-11-23 (option B for the extra scoping ideas), this folder rule covers factory URI reads only. Factory MCP tools, reads and writes, keep the [PRD 25](../prd/25-typescript-runtime-cli-mcp-operation-boundaries.md) R-ACCESS-6 check of project grants and target scope. The target is the project that the call acts on. That project's own grant admits the call: a Store read grant for a read, and a Store write grant for a write. Without it, the call is refused as `store-denied`, and the message says how to grant the access. The owner chose this (option A of [register](../prd/03-open-questions-and-risk-register.md) D-075) on 2026-11-23.

**What a read never shows.** A factory URI read never shows a grant, a private claim ID, file contents, a prompt, a secret, or any other item on the never-log list. It is read-only. It opens a read-only Store session, and it never creates or migrates a Store. Without a usable Store, it returns the typed Store outcome, and its next step says to read the `.make-docs/factory/` copies in a checkout of the project.

### Rules in two forms

The rules for readiness, escalation, acceptance, and the loop exist as code where the CLI checks them, and as the factory contract for agents. A change to one form must trigger a review of the other. The factory itself still needs the CLI and the Store.

## Alternatives Considered

- **A separate factory kit outside Make Docs.** The owner chose to build it inside Make Docs and keep it there.
- **A workflow engine in Make Docs that launches and schedules agents.** It would duplicate what the person's tools already do and tie Make Docs to particular tools.
- **Keep the old no-tracker rule and the 256-character checkpoint.** It cannot record which tool holds which job, so recovery after a crash or a lost reply fails.
- **Match roles by tool name.** It breaks for every tool that the factory does not know. Capability matching works with any tool that setup can prove.
- **A zero-config mode.** It was the old path, and it rarely worked. One setup path is simpler to build and to test.
- **The person accepts every unit.** A staged backlog would stop after each unit. The owner chose acceptance at the end of the given scope.
- **No local copies of the setup.** An agent would need a CLI call to read the wiring. The owner kept the copies in a narrow, generated, read-only form.
- **Grants in committed config.** A teammate's factory would inherit one person's permission to merge or deploy. Grants stay in the Store.
- **Keep the three-part split with no resolved plan.** Config, Store bindings, and the type would stay separate, and every reader would join them on its own. A takeover could not know the exact setup that a job started under, and drift would stay a list of ad hoc checks. The owner chose one generated, digested record.
- **Make the resolved plan a step program.** Steps, conditions, and joins in the plan would turn the CLI into a workflow engine and break R-FACTORY-5. The plan stays data, and the Skill keeps the loop.
- **Grants inside the plan digest.** Each new or spent grant would make a new revision and force a new test task, though the wiring did not change. Grants stay beside the plan.
- **Let each workflow define its own status moves.** That would make the move table a small program and make takeovers harder to check. The table is fixed in the contract and versioned.
- **Let the foreman count rounds.** An agent can lose the count across a crash or a takeover. The CLI keeps it on the assignment.
- **Free-text status history and drift messages.** Free text drifts in meaning and can hold a prompt or a secret. Fixed reason codes are stable for agents and tests, and the person still gets plain words.
- **`factory status` for every project on this machine.** A person would see all factory work at once. But readiness needs each checkout's config file, and several factories can run in one project at once. The owner chose one project, grouped by checkout and run, on 2026-11-23. A machine-wide view may come later as a separate option.
- **MCP only for the agent folder's own project.** A factory MCP call for another project would be refused, and the person would use the CLI or an MCP connection in that project. The owner chose instead that the named project's own grant admits the call (D-075, option A).
- **One folder grant for factory MCP writes too.** A Store read grant in one folder would let an agent write to every project. The owner kept the R-ACCESS-6 check for writes on 2026-11-23.
- **Default to this folder.** Factory writes would act on the project of the current folder when no project is named. It is short to type. But an agent often works in one folder and runs work for a project in another folder, so a write could change the wrong project with no warning. The owner chose option A on 2026-11-23: writes always name their project. Reads keep the folder default and show which project they read.
- **A content digest of the type file as the type version.** Config must hold no digests (PRD 24 R-CONFIG-WORK-3), so the config names a plain version number, and the plan records the file digest in the Store.
