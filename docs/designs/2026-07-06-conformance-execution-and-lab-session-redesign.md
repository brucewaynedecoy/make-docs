# Conformance Execution and Lab Session Redesign

## Purpose

This design defines the W18 R13 round: a redesign of the execution layer and asset organization of the W18 R9 conformance lab. It exists because the first attempt to operate the committed machinery — projecting the `codex-plugin-marketplace-install` scenario into a hand-runnable operator walkthrough on 2026-07-06 — confirmed that the committed scenario specs were never executable as written ([D-023](../prd/03-open-questions-and-risk-register.md)), that the mandated `.make-docs/conformance/` transcript home regresses the no-repo-run-residue principle ([D-024](../prd/03-open-questions-and-risk-register.md)), and that the harness-named `codex-*` spec identities bifurcate the tuple-dimension model the lab itself defines ([D-025](../prd/03-open-questions-and-risk-register.md)).

The user's decisions, captured here as the authoritative direction: scenario **definitions organize by domain and are harness-agnostic; evidence organizes by execution target; the per-target execution kit is generated on demand** — a permanent direction leaning hard away from harness-as-identity (D2, D3). **Agent-driven self-assessment replaces the human-operator runbook as the primary execution mode**, governed by the named rule "the agent drives, the instruments measure" (D1, D4–D7). **All three operator modes are first-class** (D9). **Ingestion bridges instrument outputs into the existing recording seam**, which does not change (D10). **The repo-local transcript home is rejected**, and the operational vocabulary becomes "lab session" so "run" is no longer overloaded (D11).

The boundary is sharp: the tuple registry, the three statuses, verdict derivation, the install-discover-invoke-uninstall evidence bar, blocked-honesty semantics, support-claim governance, and meta-verification semantics are all UNCHANGED by this redesign (D13). Only how evidence gets produced — and how the assets that describe its production are organized — changes. The round is tracked as register item [R-028](../prd/03-open-questions-and-risk-register.md), whose mandate this design's reconciliation inventory (D12) exists to satisfy: nothing under the rug.

## Context

**What exists and is sound.** W18 R9 landed the conformance machinery end to end: the eight-dimension support tuple (`packages/cli/src/conformance/tuple.ts`), the fail-closed tuple registry (`conformance/tuple-registry.json`, loaded by `registry.ts`, statuses rederived from evidence on every load), the four-stage evidence bar with verdict derivation as byte-compared data, the single recording seam `recordConformanceRunOnRegistryEntry` in `scenario.ts` producing `conformance.result.v1` records, three machine-enforced test layers, the R-TEST-1..3 meta-verification checks, and registry-derived support-claim governance with machine-checked `support-claim-state` markers on four claim surfaces (0 of 20 tuples conformance-validated). The relocation of the asset family to repo-root `conformance/` (D-022, former PRD 42; current authority [PRD 43](../prd/43-conformance-scenario-model-and-execution-kits.md#canonical-conformance-asset-home)) stands and is not revisited.

**What failed.** The execution layer — the part that turns a spec into a real session against a real harness — was designed as a human-operator protocol and never actually driven. When it was driven (as a projection, without touching a harness), three defects surfaced and were verified against code: the specs' ship commands omit `--support-evidence-ref` and the planner unconditionally raises a `missing-support-evidence` stop that aborts `ship` before writing; the specs' non-TTY `setup remove --backup < /dev/null` uninstall step cannot pass the TTY confirmation gate without the `--yes` the specs omit; and the specs' workspace steps never establish the packaging precondition attestations the ship step requires. The R-TEST-2 "runnable" check verified structure — existence, bar-eligibility, linkage, fixtures, probeable preconditions — but nothing ever projected the literal step text against the real command surface. This is the library-without-wiring pattern (D-021) recurring at the protocol layer: spec-without-execution.

**What was mis-organized.** The four committed specs are named `codex-*` and carry a `futureHarnesses` property that implies a copy per harness — fusing the scenario dimension (a user outcome) with the harness dimension (an execution target) that the registry, the tuple, and the [conformance README](../../conformance/README.md)'s own Scope paragraph keep separate. And the raw-evidence home `.make-docs/conformance/` — mandated by [PRD 20](../prd/20-agent-harness-conformance-and-support-claims.md) and carried by PRD 37, the `.gitignore`, code defaults, test fixtures, and guides — is a second ad-hoc repo-local `.make-docs/` family that regresses the W18 R7 run-state principle completed by W18 R10 (PRD 35/38): run residue lives in the machine-level store, never repo-local `.make-docs/`.

**Raw material.** The parked, deliberately untracked `CONFORMANCE-RUN-codex-plugin.md` at the repo root is the user's working file: a complete human-operator walkthrough of the plugin scenario with the three spec defects recorded in boxed notes. It is evidence and raw material for the human-only operator mode (D9); agents never modify it. The negative Codex v0.142.4 recognition probe and the committed characterization preamble that plans its resolution (R-021) are the opening real-harness inputs any execution form must serve; the characterization intent must survive the redesign (D8).

## Decision

### D1. Named design rule: the agent drives, the instruments measure

R-EXEC-1 (MUST). Self-assessment is never self-attestation. In every execution mode, the target agent (or human operator) performs the discovery, invocation, and judgment-shaped work — but conformance evidence comes exclusively from deterministic instrument outputs: probe marker files, exit codes, listing captures, file inventories, and byte-level before/after uninstall diffs. A target agent's claim ("the skill appeared", "the plugin installed") is narrative context, never evidence; a bar stage with no instrument output is unasserted, full stop.

R-EXEC-2 (MUST). Uninstrumentable stages are recorded caveats, not trust fallbacks. Where a stage genuinely cannot be instrumented for a target (for example, a harness whose listing has no machine-readable capture), the session records the gap as a caveat on the result record — feeding the existing `pass-with-caveats` rules, which require surfaced caveats to advance a tuple — and never substitutes the agent's or operator's say-so for the missing instrument.

R-EXEC-3 (MUST). Blocked-honesty semantics are preserved unchanged: unmet preconditions resolve to an honest `blocked` result record (`supportClaimUse: none`, all-false evidence bar) exactly as PRD 37 and the W18 R9 machinery already enforce. The redesign changes who drives, not what counts.

### D2. Organization: definitions by domain, evidence by target

R-ORG-1 (MUST). Scenario definitions are harness-agnostic and live under `conformance/scenarios/<domain>/`. The first and only current domain is `packaging` (the four first-pass outcomes); `playbook-runs` is the named future domain (conformance of run orchestration outcomes) and is created only when its first definition lands. Definition ids are domain-qualified outcome names with no harness token: `packaging/plugin-marketplace-install`, `packaging/skills-bundle-discovery-invocation`, `packaging/dependency-check-both-directions`, `packaging/uninstall-backup-cleanliness`, each at `conformance/scenarios/<domain>/<outcome>.json`.

R-ORG-2 (MUST). Evidence and results organize by execution target: committed result records live at `conformance/results/<harness>/<YYYY-MM-DD>-<outcome-slug>-<seq>.json`, where the directory key is the harness id and the model-or-provider and runtime dimensions live inside each record (they are already record fields; deeper directory nesting is deferred until volume demands it). The tuple registry remains the single queryable index across all targets — the directory layout is storage, not a second query surface.

R-ORG-3 (MUST). The committed README Scope paragraph — conformance is not harness-specific; harness is one dimension of the eight — survives and extends with the domain axis: a scenario domain groups outcome definitions by product area, and neither domain nor scenario ever encodes an execution target. `conformance/fixtures/` is unchanged in location, contract, and contents.

### D3. Scenario schema: target bindings replace harness identity

R-SCHEMA-1 (MUST). The `conformance.scenario.v1` lab core is untouched. The `packagingExtension` block survives but is revised: it keeps the definition-level, target-independent fields — the per-stage `evidenceBar` assertions, `transcriptPolicy`, `workspacePolicy`, `fixturePlaybooks`, and the precondition *template* (which preconditions exist and which are attestation-only) — and gains `domain`. The fields that name a target move out of the definition body: `harness` (deleted as a top-level extension field), `harnessExecution`, per-target `registryTupleIds`, and target-specific precondition probes live in a `targets` map keyed by harness id.

R-SCHEMA-2 (MUST). `futureHarnesses` is retired. Its honest job — "these harnesses are not covered, say so" — is done structurally: a harness with no entry in a definition's `targets` map is an uncovered target, kit generation for it fails closed naming the gap, and the registry's existing scenario-absence notes (R-SCEN-2) continue to report it. Absence is still reported, never implied as covered; it just stops requiring a hand-maintained list that implies a copy-per-harness future.

R-SCHEMA-3 (MUST). `REQUIRED_FIRST_PASS_SCENARIOS`, the R-TEST-2 check, and the registry's `plannedScenarios` values move to the new domain-qualified ids in the same change as the definitions (see D12); the required first-pass set remains exactly the four packaging outcomes bound to Codex targets.

### D4. The kit: per-target, generated, disposable

R-KIT-1 (MUST). A conformance kit is generated on demand for one (definition, target) pair — or one target's full first-pass suite — into a disposable lab-session workspace outside the repository (under the OS temp root or the machine-level store's lab area, per D11). The kit contains: (a) the **artifacts** the target needs — the fixture project materialized and the generated distributable(s) shipped through the real packaging pipeline (plan/preview/write via the same compiler and descriptors the product ships, with evidence refs and precondition attestations supplied by the kit's session configuration rather than remembered by an operator — the structural fix for all three D-023 defects); (b) the **prompts** directing the target agent's self-assessment (D7); (c) the deterministic **instrument scripts** per bar stage (D6); and (d) a **session manifest** recording the definition id, target, tuple ids, generation inputs (descriptor digest, CLI version), and the expected-evidence table the ingest step validates against.

R-KIT-2 (MUST). The workspace layout is fixed: `<session-root>/kit/` (prompts, instruments, manifest), `<session-root>/workspace/` (the fixture project the target operates in), `<session-root>/evidence/` (instrument outputs and transcripts). The workspace is disposable by default — discarded after ingestion — and nothing in it is ever written under the repository.

R-KIT-3 (MUST). Executable-by-construction: kit generation derives every command it emits (packaging invocations, `setup remove --yes` forms, precondition establishment) from the registered operation surface and the capability descriptors, and fails generation — before any session starts — if a definition cannot project to a command sequence the current CLI accepts. This is D-023's close-bar direction as machinery.

### D5. Kit generation home: maintainer lab tooling, not a shipped operation

R-HOME-1 (MUST). The kit generator is lab code in `packages/cli/src/conformance/` (a `kit.ts` module beside the existing lab modules, so it consumes the descriptors, the packaging pipeline, and the scenario loaders in-process and is unit-testable), invoked through maintainer tooling (an npm script/`scripts/` entry in this repo). It is deliberately NOT registered in the operation registry and NOT exposed on the shipped CLI command tree or MCP surface.

Rationale, weighing the W18 R11 parity rule: R11 binds the *shipped* command surface to the operation registry — every shipped command is a registered operation and vice versa. Kit generation stays off the shipped surface entirely, so parity is preserved vacuously rather than violated. Shipping it as an operation would advertise a maintainer-lab capability whose required assets are structurally excluded from every install (R-TEST-3 keeps `conformance/` out of all shipped trees), producing a command that can never succeed for a user — the same category error D-022 fixed at the directory level. The revisit seam is recorded on [Q-022](../prd/03-open-questions-and-risk-register.md): if the agentics production pipeline ever makes lab surfaces first-party, registration is reconsidered then.

R-HOME-2 (MUST). The kit generator CONSUMES the harness capability descriptors and never mints a second home for harness knowledge (PRD 36 R-CAP-2). Where a kit needs harness knowledge the descriptors do not yet carry — how to list installed plugins, where a harness logs skill invocation — that knowledge is authored INTO the descriptor (a lab-facing interrogation block on the descriptor type, verification-marked like every other descriptor claim), and the kit renders from it. A kit-local table of harness facts is the R-021 regression vector and is prohibited.

### D6. Instruments: deterministic, machine-verifiable, one per bar stage

R-INST-1 (MUST). Each asserted bar stage has an instrument script in the kit whose output is machine-verifiable and lands in `evidence/`: **install** — exit codes of the install commands plus a file inventory of the harness-visible placement roots; **discover** — a capture of the harness's own listing surface (command output, directory listing, or manifest read, per the descriptor's interrogation block) that the ingest step greps deterministically; **invoke** — the fixture skill's deterministic invocation marker (the existing `conformance-skill-probe` emits it) captured as a probe file; **uninstall** — a byte-level before/after diff of the placement roots and the workspace proving managed outputs removed, user content untouched, no orphaned managed directories. Instruments capture; they never interpret — interpretation happens at ingestion against the manifest's expected-evidence table.

R-INST-2 (MUST). Instruments are deterministic and offline: no instrument spends network or model routing. The expensive, judgment-shaped middle — getting the harness to actually exercise the artifact — belongs to the driving agent or human; the instruments bracket it with measurements.

### D7. Prompts: target-agnostic core, per-target rendering

R-PROMPT-1 (MUST). The kit's prompt set has a target-agnostic core — the session narrative: what outcome is being assessed, the honesty rules verbatim (blocked is a valid result; failures are evidence; assertions never relax), the instruction to perform its own discovery and assessment, when to run each instrument, and the explicit statement that its claims are not evidence and only instrument outputs count — rendered per target with the harness-specific specifics (names, paths, invocation phrasing) drawn from the descriptors. The prompt tells the target agent to attempt, observe, and narrate; it never asks the agent to certify.

### D8. The discovery kit: the characterization preamble's new form

R-DISC-1 (MUST). The characterization preamble committed on the plugin scenario (R-021's resolution plan for the negative Codex v0.142.4 probe) carries forward as a **first-run discovery kit**: a kit variant whose session precedes bar assertion and whose instruments record ground truth — pin the harness version, hand-author a minimal plugin from the harness's own docs independent of Make Docs, vary marketplace source shapes until one is accepted, capture the accepted shape, then diff the generated shapes against it. Discovery findings feed **descriptor corrections**: divergences are compiler or descriptor defects to fix (re-triggering the contract-digest re-verification), never relaxations of the evidence bar. The schema's `characterization` block is renamed and generalized to `discoveryKit` with the `resolvesProbe` linkage to R-021 preserved verbatim, and the plugin definition's target binding for Codex carries it.

### D9. Operator modes: three, all first-class

R-MODE-1 (MUST). The lab documents three execution modes, all producing evidence through the same kit and instruments: **human-only** — the manual fallback; a human generates the kit, performs every step, runs the instruments by hand; the parked `CONFORMANCE-RUN-codex-plugin.md` walkthrough is the raw material for these instructions (its content is absorbed; the file itself is the user's working file, never modified by agents, retired by the user when absorbed). **Human + assisting agent** — an agent does setup (kit generation, workspace preparation, ingestion) while the human drives the target harness and prompts its self-assessment. **Agent-multiplexed** — an orchestrating agent uses a terminal-multiplexer tool to launch the target harness, deliver the prompts, monitor the session, and run instruments end to end; the multiplexer tooling is consumed as an environment capability, not built by Make Docs.

R-MODE-2 (MUST). Mode instructions live at `conformance/operator-modes.md` — executable protocol content, which is exactly what the maintainer-only `conformance/` directory holds per D-022 — with the developer conformance-lab guide summarizing and linking rather than duplicating.

### D10. Ingestion: instruments in, the existing seam out

R-ING-1 (MUST). Ingestion is a deterministic kit step that assembles a `conformance.result.v1` result record from the session: bar-stage booleans derive SOLELY from instrument outputs validated against the manifest's expected-evidence table (a missing or failed instrument output for an asserted stage yields `false` — fail-closed, no narrative rescue); the driving agent or human contributes only what instruments cannot — the operator attestations (network, model routing), the run metadata (model, provider, runtime), and the narrative `reason` — and every attestation is recorded as an attestation, distinguishable from measurement. The assembled record validates against the existing result contract before it goes anywhere.

R-ING-2 (MUST). The recording seam is unchanged: the validated record is committed under `conformance/results/<harness>/` and bound to its registry tuple exclusively through `recordConformanceRunOnRegistryEntry`, whose existing refusals (unasserted stages, tuple or harness mismatch, simulation-posture mismatch) and the registry's existing derivation rules do all the gating they do today. Nothing new writes to the registry; nothing bypasses the seam; the R-TEST-1 receipts discipline (record resolves, validates, projects back byte-equal) applies as-is.

### D11. Naming and evidence homes: lab sessions, no repo residue

R-NAME-1 (MUST). The operational envelope is a **lab session**: session id, session workspace, session evidence, session manifest. "Run" survives in exactly two prior meanings that do not change — the registry's `recordedRuns` projection (a recorded run is the evidence-layer noun, per the unchanged contracts) and the `run` CLI command — and is never used for the operational envelope, its directories, or its tooling. No new artifact, path, or identifier uses "run" for lab operations.

R-NAME-2 (MUST). Per the user's decision, the `.make-docs/conformance/` transcript home is rejected (D-024): transcripts and evidence scratch live in the disposable session workspace and are discarded with it by default; deliberately redacted-and-promoted evidence lands in the committed result record; raw evidence retained beyond a session (kept transcripts, provider logs) goes to the machine-level store's lab area (`<store-root>/conformance-lab/sessions/<session-id>/`), never repo-local `.make-docs/`. The `.gitignore` entry, the `scenario.ts` default transcript pointer, the `registry.ts` commentary, and the test-fixture pointers all move off the old path at implementation (D12); `transcriptLogPointer` values in result records point into the store's lab area or state `discarded-with-session`.

### D13. Non-goals

The tuple registry schema, statuses, and derivation rules; the evidence bar and verdict vocabulary; blocked-honesty and simulation-posture semantics; support-claim governance, thresholds, and claim surfaces; and the meta-verification semantics (beyond the id/path retargeting and the added executability check) do not change. The implementation round performs no real-harness interaction — it builds the kits, instruments, ingestion, and reorganization; operating lab sessions against a real Codex install is the subsequent operational work that R-021/R-022 gate on. Terminal-multiplexer tooling is consumed, not built. No new public claim surface is created. Claude Code and Pi target bindings extend only as far as their (still provisional) descriptors honestly allow; their absence from first-pass coverage remains reported, not implied as covered.

### D14. Verification

The implementation must prove: kit generation fails closed on an unprojectable definition and the D-023 defect classes are impossible in generated output (evidence refs, `--yes`, precondition establishment all kit-supplied — asserted by tests over generated kits); ingestion refuses to assert a bar stage without its instrument output; the R-TEST-2 check passes over the domain-organized definitions and the executability check runs enforcing in the standard suite; the reconciliation greps return no live-surface hits (`.make-docs/conformance` outside dated evidence and the preserved compiler record, `codex-*` scenario ids, `futureHarnesses`, stale `REQUIRED_FIRST_PASS_SCENARIOS` ids); the registry loads green with updated `plannedScenarios` and untouched statuses; and the standard validation surface (CLI suite, build, `validate:defaults`, `smoke:pack`, path hygiene) is green. Unit and integration tests over kits and instruments remain repository layers and are never cited as harness-recognition evidence (R-LAYER-2/R-TEST-5 unchanged).

## Alternatives Considered

**Patch the three spec defects in place.** Rejected: it would polish artifacts whose form (harness-named, human-runbook-projected, hand-transcribed commands) is the root cause D-023 names; the next spec would drift the same way because executability would still be authored, not generated.

**Copy-per-harness specs (the `futureHarnesses` direction).** Rejected as the bifurcation D-025 records: N×M spec copies with independently drifting shared assertions, contradicting the tuple model and the README's own Scope paragraph.

**Keep a committed or gitignored repo-local transcript home.** Rejected per the user's decision (D-024): it regresses the no-repo-run-residue principle the store architecture established and hardens the "run" overload into paths.

**Ship kit generation as a registered operation.** Rejected for now (D5): it would put a command on the shipped surface whose required assets are structurally excluded from every install — the directory-level category error of D-022 repeated at the command level. Revisit seam recorded on Q-022.

**Trust the target agent's structured self-report as evidence.** Rejected absolutely (D1): self-assessment without instruments is self-attestation — the files-written-equals-works failure re-imported at the evidence layer, which is the one place the lab exists to keep it out.

**A new recording pathway for kit outputs.** Rejected: `recordConformanceRunOnRegistryEntry` and the result contract already gate everything that needs gating; a second seam would be the parallel-truth pattern the registry design forbids.

## Consequences

The first-pass evidence R-021 and R-022 wait on becomes producible in three modes instead of one, with the cheapest honest path (agent-multiplexed) available where the environment provides a multiplexer and the manual path preserved where it does not. Spec defects of the D-023 class move from mid-session surprises to generation-time failures. The scenario set stops multiplying by harness: covering Claude Code later means adding target bindings and descriptor knowledge, not spec copies. Harness knowledge concentrates further into the descriptors (D5's interrogation block), strengthening the R-CAP-2 single home and giving the discovery kit a precise correction target. The costs: a real reconciliation surface (D12's twenty entries — the price of never having two truths), a schema revision on a young contract (acceptable now for the same reason the v2 playbook break was: nothing external consumes it and zero result records exist), and new maintainer-only code (kit generator, instruments, ingestion) that must itself be tested without ever being mistaken for conformance evidence — the existing layer discipline already polices that. The kit generator also becomes the packaging pipeline's first end-to-end internal consumer, which is exactly the dogfood Q-022's production-pipeline lineage wants before it commits.
