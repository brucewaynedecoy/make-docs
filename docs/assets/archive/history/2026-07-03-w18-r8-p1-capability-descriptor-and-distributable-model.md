# W18 R8 P1 Capability Descriptor and Distributable Model

## Changes

Implemented [Phase 1 of the W18 R8 backlog](../../../work/2026-07-01-w18-r8-playbook-packaging-compiler-and-harness-adapters/01-capability-descriptor-and-distributable-model.md) per [PRD 36](../../../prd/36-revise-playbook-packaging-compiler-and-harness-adapters.md) R-CAP-1 through R-CAP-5 with R-ADAPT-1 and R-MKT-1 structural support, all nine phase tasks (t1 through t9) checked off. The new `packages/cli/src/operations/playbook-packaging/capability-descriptor.ts` defines the harness capability descriptor as the single home of harness-specific packaging knowledge (R-CAP-2): harness id, supported agentic primitives (`skill`/`plugin`/`extension`/`hook`/`mcp-server`), containers with kind, native-or-portable profile, richness rank, hosted primitives, per-surface/per-scope path placements, manifest filename, skill file template, and registration files, a lifecycle event map from logical events to harness hook points, exposure modes, a registration model whose `autoRegister` is typed `false` so a marketplace is never auto-mutated (R-MKT-1), preconditions, and a verification block with status, reference, and provisional notes (R-ADAPT-1) — with invariant validation at construction and `deriveAdapterDeclarationCore`/`deriveAdapterPathTemplates` deriving the adapter-facing shapes. `descriptors.ts` carries the first-party data: `codex` declares the verified `.codex-plugin/plugin.json` manifest and `.agents/plugins/marketplace.json` registration on the container per R-ADAPT-2 while its placement roots deliberately keep the W18 R5 shapes pending the Phase 3 verification pass; `claude-code` maps five session events to `SessionStart`/`SessionEnd`/`UserPromptSubmit`/`PreToolUse`/`PostToolUse` with the git events deliberately unmapped so event-bound steps on them degrade or fail closed; `pi` supports skills, extensions, and MCP but not hooks, its richest native container is an extension, and all of its paths are inferred and flagged; the fixture descriptor exercises additive registration. Every first-party descriptor is `provisional` pending Phase 3 real-harness verification, so no descriptor content is harness-recognition evidence (R-TEST-5).

The new `packages/cli/src/operations/harness-registry.ts` is the one registry serving both capability questions (R-CAP-1): entries keyed by canonical harness id carry the packaging descriptor plus an identity-only `runtimeCapability.recordKey` link, `canHarnessHostPrimitive` answers the packaging-time question, and the W18 R7 `evaluateHarnessCapabilities` keeps the run-time question entirely — it now resolves its config-record key through `resolveRuntimeCapabilityRecordKey` with unregistered ids passing through unchanged, so identity is shared and semantics are untouched. `distributable.ts` implements the two-granularities model (R-CAP-3 through R-CAP-5): `projectPlaybookToSkill` fixes one Playbook to one skill with persona qualification only on slug collision, `deriveImpliedAgentics` reads the parsed W18 R6 model (event-bound steps imply a hook, mcp executors/dependencies an mcp-server, plugin/skill/playbook dependencies their primitives), and `selectPackageContainer` picks the richest profile-matching container — `plugin` resolving to the richest native container per descriptor, an extension for Pi, and `skills-bundle` to the portable agents-standard form — lowering each agentic as native with its hook point, `degraded-skill-instruction`/`degraded-manual-step` under the `degrade` policy, or a fail-closed unsupported-surface stop under the default `fail-closed` policy, with the policy and every lowering declared in plan `fieldProvenance`, `deterministicDerivations`, and dry-run lines. `adapters.ts` now derives path templates, preconditions, and exposure modes from the descriptors with byte-identical derived output (resolver and writer untouched), `planner.ts` stays harness-neutral through registry delegation, the W18 R5 target model is preserved unchanged, and the Pi adapter is deliberately absent until Phase 3. The suite closed at 795/795 (+20 in the new `packages/cli/tests/playbook-packaging-capability.test.ts`) with the build green; no template-package resource was implied, so no upstream authoring was needed.

Developer-guide coverage was `update-existing` on [Playbook Packaging and Harness Adapters](../../library/developer/playbooks-development-packaging-and-harness-adapters.md), which owns the packaging topic: it gained three sections — Harness Capability Descriptors (the single-home rule, the descriptor fields, the type-enforced `autoRegister: false`, the first-party descriptor inventory with its deliberate provisional caveats, and the R-TEST-5 boundary that descriptor content is never recognition evidence), Shared Harness Registry (both questions, one registry, the identity-only runtime link, and the split extenders must keep), and Two-Granularities Distributable Model (one Playbook to one skill, implied agentics from the parsed model, richest-container interpretation of `outputKind`, declared degradation with the default fail-closed policy, and the not-yet-wired `unsupportedPrimitivePolicy` plan input) — plus the adapter-derivation and Pi-absence updates in the adapters section, the new capability test-file coverage note, the how-to-add-a-harness recipe (descriptor, adapter, registry entry, fixtures, conformance scenarios; never planner conditionals), and a new Future Coverage section whose two bullets name the Phase 2 compiler rebuild and the Phase 3 verification pass as the update triggers. [Run Playbook Runner Architecture](../../library/developer/playbooks-development-runner-architecture.md) received a link-only addition, because it owns `evaluateHarnessCapabilities` and a reader changing the evaluator needs to know the registry now supplies its record key by identity without owning any of its semantics. No new developer guide was warranted — the existing guide owns the topic exactly.

User-guide coverage was `update-existing` on [Packaging Shareable Playbook Workflows](../../library/user/playbooks-packaging-shareable-agent-workflows.md) at minimal, honest scope, because Phase 1 is model and planner work with a small user-visible surface: the Output Choices section now explains `plugin` as the richest package the target harness natively supports (an extension where that is the richest native form) and `skills-bundle` as the portable standard form, and states the one behavior a reader can see today — the package plan lists the package's skills and declares every downgrade or unsupported-surface stop so nothing is silently dropped. The `unsupportedPrimitivePolicy` plan input was deliberately not documented for users because no CLI flag exposes it yet; the Future Coverage bullets were re-anchored from the completed W18 R5 to the real blockers, the W18 R8 Phase 2 compiler surfaces (which now also carry the degrade-versus-stop choice) and the W18 R9 conformance evidence. No new user guide was warranted.

PRD coverage was `risk-register-update` with no change doc, because the phase implemented existing PRD 36 requirements without changing the requirement surface. [R-017](../../../prd/03-open-questions-and-risk-register.md) advanced in place: its Decision now records the W18 R8 P1 landing — descriptor as single home, byte-identical adapter derivation, the shared registry with runtime semantics untouched, and the two-granularities distributable with declared degradation riding the plan — while stating honestly that the writer still emits the descriptor-era payload until Phase 2. [R-021](../../../prd/03-open-questions-and-risk-register.md) advanced in place: its Decision now records that the verification rule is structural — every descriptor carries the typed verification block, all first-party descriptors are provisional with notes naming exactly what Phase 3 must confirm, the Pi adapter is deliberately absent, and `autoRegister` is typed `false`. Both items stay Open because their close bars require the Phase 3 verified adapters and the W18 R9 conformance evidence. No other register item needed movement (R-016 is runner-side and untouched; R-022 concerns conformance scenario availability, which this phase does not advance), the PRD 36 baseline text needed no change note (implementation, not requirement change), and `docs/prd/00-index.md` needed no maintenance.

Testing and UAT coverage beyond the suite was `none`: the phase ships no new end-user command surface — the only observable deltas are new plan JSON fields and dry-run lines already asserted by the 795-test suite, and the `unsupportedPrimitivePolicy` input has no CLI flag until Phase 2 wires surfaces — so a manual pass would re-drive covered assertions without adding signal; the W18 R8 UAT moment is the Phase 3 real-harness recognition work, which R-TEST-5 explicitly reserves for the conformance lineage.

Validation: full CLI suite 795/795 with the build green, `npm run validate:defaults` exit 0, `python3 .make-docs/scripts/check_path_hygiene.py` clean, relative links in the touched docs verified to resolve, no guide promoted past `draft`, no unresolved placeholders, and `git diff --check` clean for every doc this session touched.
