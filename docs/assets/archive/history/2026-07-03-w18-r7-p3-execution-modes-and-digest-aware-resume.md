# W18 R7 P3 Execution Modes and Digest-Aware Resume

## Changes

Implemented [Phase 3 of the W18 R7 backlog](../../../work/2026-07-01-w18-r7-run-playbook-state-machine/03-execution-modes-and-digest-aware-resume.md) per [PRD 35](../../../prd/35-revise-run-playbook-state-machine.md) R-MODE-1 and R-MODE-2, R-RESUME-1 and R-RESUME-2, and the R-TIER-1 CLI-absent groundwork, with all eight phase tasks (t1 through t8) checked off. The new deterministic-execution module at `packages/cli/src/operations/playbook/execution.ts` executes a `deterministic` step's `operation` through `invokeOperation` in the operation core — importing the registry lazily at call time to avoid a module-initialization cycle, and running the step as the `playbook-step` third registry surface whose execution context inherits the advancing caller's `writesAllowed`, `dryRun`, and `approvals` — and its `command` through `spawnSync` with `shell: true`, `cwd` at the run's repository root, and a ten-minute ceiling. `advancePlaybookRun` in `progression.ts` is now async and mode-aware and returns `{state, execution}`, the execution report carrying the step id, effective mode, action, outcome, presented command, presented instructions, and structured execution evidence. Deterministic steps execute BEFORE the state transition so a thrown execution error leaves the stored run untouched; gating refusals (write denied, missing approval, pending identifier) propagate as advance-level errors and are never recorded as fake step failures, while handler failures, non-zero exits, timeouts, and spawn failures resolve to `failed` outcomes the routing handles; a reported outcome on a deterministic step is accepted as the by-hand execution report. The CLI-absent path (`present: true`) resolves and presents the human command form and holds the step at `waiting-for-user` with idempotent presentation evidence — the command form is derived from the new `operationCliPath`/`operationCliCommand` single derivation rule in `packages/cli/src/operations/registry.ts`, which `run/cli.ts` now also consumes, removing the hand-maintained spelling. Delegated steps — including the R-MODE-2 unspecified-mode default — present instructions and hold for a later advance carrying outcome plus evidence, and manual steps require `--acknowledge`, refuse outcomes, and execute nothing. `playbook.resume` landed the digest check at the Phase 2 `PHASE 3 SEAM (R-RESUME-1)` marker: a matching digest resumes at the stored cursor and clears staleness; a mismatch durably marks the run stale and blocked (the new additive `PlaybookRunStaleness` field, with the record's `schemaVersion` staying 2) then throws a diagnostic naming the playbook path, both digests, and the step-identifier diff, pointing to re-plan or `--migrate`; stale runs refuse `advance` and `gate`. Migration is opt-in only: it re-keys statuses by step id, seeds added steps `pending`, drops removed steps and names them in evidence, keeps the surviving cursor (falling back to the first pending sequential step), merges the dependency snapshot, and adopts the current digest, schema versions, and routing model — the algorithm recorded as a D9-style implementer decision on `migratePlaybookRun`. Evidence records gained the structured `PlaybookRunExecutionEvidence` result (form, operation or command, exit code, stdout/stderr 4000-character tails, result summary, error message, truncation flag). The CLI gained `--acknowledge`, `--present`, and `--migrate`, `--outcome` became optional, and the MCP schemas derive automatically from the updated zod contracts. Coverage grew by eight tests to 752/752 across 45 files — the full mode matrix, presentation idempotence, stale-block diagnostics, and a migration round-trip — with the build green.

Developer-guide coverage was `update-existing` on [Run Playbook Runner Architecture](../../library/developer/playbooks-development-runner-architecture.md), which owned the topic and carried a Future Coverage bullet blocked on exactly this phase plus Phase 4: the Progression Engine section gained the mode-execution architecture (the `execution.ts` module, the lazy registry import, the `playbook-step` third-surface execution context, the before-transition ordering and refusal-versus-failure distinction, the presented-command and acknowledgment paths) and replaced the Phase 2 resume-shell paragraph with the digest-checked re-entry, the durable staleness marker, the stale-run advance/gate refusal, and the opt-in migration semantics; the Entry Points bullets for `advance` and `resume` picked up the new flags and the optional `--outcome`; the Run State record description now lists the execution evidence and the staleness marker; and the shared registry-to-CLI derivation (`operationCliPath`/`operationCliCommand`) is documented as the single spelling rule. The Future Coverage bullet was resolved for its Phase 3 half and re-scoped to the Phase 4 guardrails, portability, and three-tier degradation work, keeping the invoke-collapse question. No new guide was warranted because the runner-architecture guide owns the whole runner story. User-guide coverage was `update-existing` on [Running Make Docs Playbooks](../../library/user/playbooks-running-make-docs-workflows.md): the Driving a Run from Start to Close section now explains advance per execution mode — deterministic steps that execute themselves and capture their own evidence, `--present` for by-hand execution, the delegated default that holds for a reported outcome with evidence, and `--acknowledge` for manual steps — and the resume walkthrough now documents the digest check honestly: the stale-block behavior with its three options (fresh `start`, revert and resume, or explicit `--migrate`) and what migration keeps, seeds, and drops. The Phase 4 guardrails and the three-tier degradation proof were deliberately not claimed. The user guide's own Future Coverage bullet (a reader-facing Playbook-contract projection) stays unresolved because its trigger is the broader W18 R7 runner migration, which still has Phases 4 and 5 open. PRD coverage was `risk-register-update` with no change doc, because the phase implemented existing PRD 35 requirements without changing the requirement surface: [R-016](../../../prd/03-open-questions-and-risk-register.md) advanced in place — the Decision records the mode-aware advance, the third-surface gating inheritance, the registry-derived presented command, and the digest-checked resume with opt-in migration, and the Follow-Up drops the now-landed P3 inputs, leaving the P4 guardrails and plugin-surface parity as the remaining close inputs — staying Open because its literal close bar still requires CLI/MCP/plugin parity, and the plugin surface does not exist yet. The resume flow the R-016 close bar names is now proven for CLI and MCP, but not for plugins. No other register item needed movement: R-019 is Closed and its historical text remains accurate, and the R-017 digest mentions concern packaging provenance, not resume. `docs/prd/00-index.md` needed no change: PRD 35 remains Current and its row already names execution by step mode and digest-aware resume at requirement level.

Validation: full CLI suite 752/752 across 45 files, `npm run validate:defaults` exit 0, `python3 .make-docs/scripts/check_path_hygiene.py` clean, relative links in the touched docs verified to resolve, no guide promoted past `draft`, and no unresolved placeholders. `git diff --check` is clean for every doc this session touched and reports no whitespace findings in the implementation's uncommitted code files.
