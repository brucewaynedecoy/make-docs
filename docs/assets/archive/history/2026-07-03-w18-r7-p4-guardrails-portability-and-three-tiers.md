# W18 R7 P4 Guardrails, Portability, and Three Tiers

## Changes

Implemented [Phase 4 of the W18 R7 backlog](../../../work/2026-07-01-w18-r7-run-playbook-state-machine/04-guardrails-portability-and-three-tiers.md) per [PRD 35](../../../prd/35-revise-run-playbook-state-machine.md) R-GUARD-1 through R-GUARD-4, R-PORT-1, and R-TIER-1, with R-SCOPE-2 and R-KEEP-1 capability consumption, and all ten phase tasks (t1 through t10) checked off. The guardrails are enforced at two points. Creation-time enforcement in `createPlaybookRunState` (`packages/cli/src/operations/playbook/run-state.ts`): a child run requires an open parent whose orchestration policy permits child Playbooks — a closed parent refuses new children — links through `parentRunId` plus the shared `rootRunId` propagated across nesting depth, and defaults to serial (R-GUARD-1); parallel children require ALL of explicit parent permission, parallel-execution support — a reviewed `harnessCapabilities` record with `parallel_playbook_runs: true` consumed unchanged or the explicit `parallel-children-reviewed` approval riding the operation core's named-approval seam — and output-surface claims disjoint from the parent and every sibling, with each refusal naming the serial fallback, and a reviewed record that does not support parallel still stopping parallel children (R-GUARD-2); a new run's claims are checked against every unrelated open run of the project, stopping creation on overlap and unblocking when the conflicting run closes, with the serial ancestor chain the recorded R-GUARD-3 concurrency exemption on `playbookRunFamilyIds` so a serial child may claim inside its parent's surfaces; the unattended opt-in fails closed when the Playbook's run metadata does not declare `unattended: true` (R-GUARD-4); and a `manual-review-required` capability snapshot creates the run `blocked` with the evaluation's guidance while a `serial-gated-fallback` snapshot records its guidance as resume hints (R-SCOPE-2, R-KEEP-1). Transition-time enforcement in `progression.ts`: `requireCapabilityClearance` refuses `advance`, `gate`, and `resume` on a `manual-review-required` snapshot with `close` staying available; `requireStepOutputSurfacesFree` stops an advance whose step-declared output surfaces overlap another open run's claims before anything executes, so writes are never interleaved (R-GUARD-3); and `settleUnattendedGates`, applied at step advance and gate approval, auto-approves only gates declaring `unattended: true` in an unattended run — recording each approval as a gate decision with evidence — and holds every other gate at `waiting-for-user` (R-GUARD-4). Portability landed as the new `packages/cli/src/operations/playbook/portability.ts`: `exportPlaybookRun` serializes the run record and its evidence into one portable JSON artifact — format `make-docs.playbook-run-export`, version 1, with the artifact shape and the identity-on-import rule recorded as D9-style implementer decisions in the module doc — returned inline by default and written ONLY to an explicit caller-named output path, never a repository default; `importPlaybookRun` validates the artifact fail-closed, refuses an existing run id without the explicit overwrite opt-in, refuses a cross-project artifact unless the `adoptProject` re-key is explicitly adopted, keys the rehydrated run by the importing repository's manifest-minted project identifier, and appends a new `import`-scope evidence record preserving provenance (R-PORT-1). The pair is registered as the write-gated `playbook.run.export` and `playbook.run.import` operations, surfaced as `make-docs run playbook run export --run-id <id> [--output <path>]` and `make-docs run playbook run import --artifact-json <path-or-inline-json> [--overwrite] [--adopt-project]` with MCP parity through the derived `make_docs_playbook_run_export` and `make_docs_playbook_run_import` tools; `run playbook start` gained `--unattended` and `--parallel-children-reviewed`. The run record gained additive `executionMode` and `unattended` fields with `schemaVersion` staying 2. The new `tests/playbook-three-tiers.test.ts` proves R-TIER-1 against ONE Playbook source: tier one, a bare directory where the raw Markdown is hand-followable with no engine and no state anywhere; tier two, the parsed model plus the registry-documented human command forms (`operationCliCommand`) with zero writes and zero tracking; tier three, the full engine from start through advance to close recording state in the global store with the repository byte-identical. Coverage grew by 22 tests to 774/774 across 48 files — `tests/playbook-run-guardrails.test.ts` (11), `tests/playbook-run-portability.test.ts` (8), and the three tier proofs — with the build green.
