# W18 R6 P3 Validator and Diagnostics

## Changes

Implemented W18 R6 Phase 3 by building the layered validator and diagnostic catalog at `packages/cli/src/playbook/validator/` per R-MODEL-4 through R-MODEL-6 of [historical closeout](2026-07-01-w18-r6-p1-playbook-contract-authoring.md) (retired action-PRD: `docs/prd/34-revise-playbook-contract-and-model.md`), as the executable enforcement of the Phase 1 contract over the Phase 2 model. The validator runs six semantic layers — structural, registry, workflow, cross-reference, consistency, and orchestration-policy shape (presence and value sets only, no runtime semantics per R-WF-8) — with each layer appending diagnostics independently so a registry error never suppresses workflow diagnostics; gate semantics are enforced in the workflow layer and persona-versus-folder agreement is diagnosed as PB-FM-012, both D6 implementer placements. The entry points are `parseAndValidatePlaybook(input)` (canonical: parse, validate, re-derive the runnable flag from combined diagnostics) and `validatePlaybook(model)` for an already parsed model, both exported from the `packages/cli/src/playbook/` library barrel so the Phase 4 `playbook.validate`/`playbook.catalog` operations and a future language server share identical diagnostics (R-MODEL-6). The exported catalog now spans twenty-four codes, PB-DOC-001 through PB-WF-024: the seven contract-fixed codes with their fixed severities (PB-DOC-001 E, PB-FM-002 E, PB-DEP-003 E, PB-DEP-004 W, PB-WF-005 E, PB-WF-006 E, PB-FILE-007 W), the four parser-structural codes from Phase 2, and thirteen validator codes from PB-FM-012 onward, with every record carrying a stable code, severity, section/field/span location, message, and fix hint (R-MODEL-5). The t10 contract parity reconciliation (R-AUTH-3) found two genuine drifts and fixed them on the contract side, authored upstream in `packages/docs/template/` and re-dogfooded byte-identically: the known event set is now enumerated (`on-session-start`, `on-session-end`, `on-user-prompt-submit`, `on-pre-tool-use`, `on-post-tool-use`, `on-pre-commit`, `on-post-commit`, `on-pre-push`, matching the exported `PLAYBOOK_KNOWN_EVENTS`), and the invocation-form rule was corrected from "exactly one" to "at most one" because a gate step declares no form — the reading already required by the design's canonical worked example — with PB-WF-005 unchanged for deterministic steps. A new test machine-checks the contract's diagnostic table against the exported catalog so contract text and catalog cannot drift silently. All ten tasks in [the Phase 3 backlog file](../../../work/2026-07-01-w18-r6-playbook-contract-and-model/03-validator-and-diagnostics.md) are checked off.

PRD coverage was the substantive pass this time, with two outcomes. First, a drift correction: PRD 34's R-WF-5 still transcribed the invocation-form rule as "exactly one", now inconsistent with the amended contract and the implementation; comparison with [the accepted design](../../../designs/2026-06-30-playbook-contract-and-model.md) showed the design's normative R-WF-5 statement never said "exactly one" (it lists the three forms and requires only that deterministic steps declare an operation or command) and its R-WF-7 worked example explicitly includes a human gate step with no invocation form, so the "exactly one" wording was PRD-side transcription drift from the design PRD 34 itself names as the normative statement of each requirement, not an established requirement being changed. Per `.make-docs/references/system/prd-change-management.md`, revisions that change an established requirement take a new numbered change doc, while discovered drift is corrected and recorded in the living register directly; this was classified as the latter, so R-WF-5 was corrected in place to "at most one ... a step that invokes nothing, such as a gate, declares no form" with no new change doc, no renumbering, and no `### Change Notes` block (those must link to a numbered change doc that carries an effective change, and none exists here). The drift and its resolution are recorded inside the existing R-018 register item rather than as a new drift item because R-018 already owns contract/validator/copy parity drift, the register rule prefers updating an existing item over duplicating, and the register consistency test pins the current item-heading set. PRD 34's other language was checked and left alone: R-WF-5 does not enumerate the event set (the design gave examples, and the contract now owns the closed enumeration) and R-MODEL-5 says the catalog includes "at least" the seven codes, so the twenty-four-code catalog conflicts with neither. Second, a risk-register update: the R-018 Decision cell in [the open questions and risk register](../../../prd/03-open-questions-and-risk-register.md) now records the Phase 3 landing (layered validator, completed catalog, machine-checked contract/catalog parity test, the two contract-side drift fixes, and the PRD 34 correction) while keeping the item Open with per-code failing fixtures, default-Playbook zero-error validation in both locations, and upstream-template-copy parity checks remaining through Phase 5; the item number, heading, Open status, and Follow-Up were preserved with a Decision-cell-only edit.

Developer-guide coverage was `update-existing` (developer persona) as a partial refresh of [the Run Playbook runner architecture guide](../../library/developer/playbooks-development-runner-architecture.md), whose Future Coverage bullet was gated on exactly this phase: the Catalog Contract Validation section now describes the landed library seam as current confirmed behavior — the six validator layers, the `parseAndValidatePlaybook`/`validatePlaybook` entry points, the twenty-four-code catalog with five-element records, the contract/catalog machine-check, and the extension rule that a new validation rule lands with its layer, catalog code, contract reconciliation, and failing fixture together — while explicitly keeping the W18 R4 catalog validation description as what the shipped operations still enforce, because nothing wires the library into operations until Phase 4. A full section replacement was rejected as premature: the runtime behavior a contributor observes today is unchanged, so the guide states both truths and the narrowed Future Coverage bullet (now blocked by Phase 4, trigger `playbook.validate`/`playbook.catalog` wiring) routes the final swap. User-guide coverage was `none` for new content because Phase 3 still has zero user-visible surface; the existing Future Coverage bullet in [the user running-playbooks guide](../../library/user/playbooks-running-make-docs-workflows.md) received an accuracy touch-up narrowing its blocker from Phases 3 through 5 to Phases 4 and 5 and noting that the landed catalog and event set strengthen the case for the deferred reader-facing contract projection once operations land. Manual-test/UAT coverage remains `none` (deferred) until W18 R6 wave completion per user instruction; the natural UAT is a `playbook.validate` run over the default Playbook once Phase 4 lands it.

Validation: the full CLI suite passed 521/521 tests at the Phase 3 implementation checkpoint and passes in full at this closeout (532 tests, the tree also carrying concurrent W18 R10 work), including the 36 new validator tests that assert each contract code with all five record elements and validate the contract worked example with zero errors and zero warnings, with the `tsc` baseline unchanged, `diff -q` confirms the upstream and dogfood contract copies are byte-identical, `git diff --check` is clean, `check_path_hygiene.py` reports zero errors on the docs touched by this closeout, all relative links in the touched docs resolve, and the jdocmunch index was refreshed. `docs/prd/00-index.md` needed no change: no doc was added, renumbered, or restatused, and its PRD 34 focus line does not quote the corrected wording.
