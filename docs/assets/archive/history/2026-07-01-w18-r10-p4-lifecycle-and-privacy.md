# W18 R10 P4 Lifecycle and Privacy

## Changes

Implemented W18 R10 Phase 4 of [historical closeout](2026-07-01-w18-r10-p5-runtime-state-guidance-and-verification.md) (retired action-PRD: `docs/prd/38-revise-global-store-and-project-state.md`) — lifecycle (R-LIFE-1 through R-LIFE-3), PRD 32 preservation, and privacy (R-PRIV-1) — across `packages/cli/`, making the store a well-behaved lifecycle citizen without adding any CLI commands or flags, because the command tree that names `setup remove` and the tool-level `uninstall`/`update` is owned by the W18 R11 reorganization (R-SCOPE-1). The new [`src/store/lifecycle.ts`](../../../../packages/cli/src/store/lifecycle.ts) carries the two seams: `pruneProjectFromStore` (R-LIFE-2) deletes exactly one project's rows across all three tables in one transaction via `deleteProjectRows`, accepts a pre-resolved project identifier because the uninstall flow must capture identity before the manifest is removed, never creates a database, and never throws — missing identity, missing store, and unusable store are explicit result statuses; `removeGlobalStore` (R-LIFE-1) is the machine-footprint removal seam the W18 R11 tool-level `uninstall` will call, and it is structurally incapable of deleting repository content: it unlinks only the fixed known store filenames non-recursively, removes the root directory only when empty, retains-and-reports unexpected entries, and refuses a root carrying project `.make-docs/` markers (the misconfigured-`MAKE_DOCS_HOME` case). The R-LIFE-1 interpretation is a recorded D10 decision in [the store module README](../../../../packages/cli/src/store/README.md): the requirement names a tool-level self-management command that does not exist yet, so the store-removal behavior lands now as the seam while the remove-or-prompt UX is deliberately deferred to W18 R11 — a prompt was rejected for the repo-level command because deleting the machine-level, all-projects store from a one-repo operation is the wrong blast radius. Today's repo-level `make-docs uninstall` ([`src/uninstall.ts`](../../../../packages/cli/src/uninstall.ts)) captures identity pre-removal, prunes that project's rows post-removal, and always prints the store disposition — pruned and kept for N other projects, last-project-gone with safe-removal guidance, no store, no identity, or an explicit prune warning — so the store is never silently orphaned. The t3 finding is that R-LIFE-3 was already satisfied at existing seams with no code change warranted: pending store schema migrations are applied by `bootstrapGlobalStore` on every apply-shaped run (proven by a new test driving `user_version` 0 to CURRENT), and pre-v2 detection with the warning-and-backup-or-cancel flow is `classifyCompatibilityState`/`guardCompatibilityDisposition` on the bare and reconfigure paths; the W18 R11 command names route through these same seams, a boundary recorded in the README. PRD 32 byte-identity holds with zero edits to backup or audit code: [historical closeout](2026-06-27-w17-r4-lifecycle-backup-state-and-agentics-pruning.md) (retired action-PRD: `docs/prd/32-revise-lifecycle-backup-state-agentics-pruning.md`) baselines (`tests/uninstall.test.ts`, `tests/backup.test.ts`, `tests/audit.test.ts`) are untouched and passing, and a new test asserts root `.backup/**` and `.make-docs/backup/**` both survive an uninstall with store handling active. The R-PRIV-1 audit found the CLI's only outbound network call is the skill-resolver manifest GET (no store fields, no project paths, no telemetry; the MCP server is stdio-local), the local-only rule plus explicit-opt-in-for-future-export is documented in the store README Privacy section, and structural tests enforce that no `src/store/**` source contains a network call or import and that the one network-capable module never imports the store. Tests landed as `packages/cli/tests/store-lifecycle.test.ts` (13 tests); the full suite passes 33 files / 550 tests and all five tasks in [the Phase 4 backlog file](../../../work/2026-07-01-w18-r10-global-store-and-project-state/04-lifecycle-and-privacy.md) are checked off.

Developer-guide coverage was `update-existing` because [the docs assets and runtime state boundaries guide](../../library/developer/maintainer-docs-assets-and-runtime-state-boundaries.md) already owns the store boundary story its P3 Future Coverage bullet gated on Phase 4: its Machine-Level Global Store boundary rules gained the seam-first lifecycle framing (prune-exactly-one-project, store removal structurally incapable of touching repository content, no new commands here), the never-silently-orphaned disposition reporting with the wrong-blast-radius rationale and the W18 R11 seam boundary, the verified-at-existing-seams update/pre-v2 story, and the structurally enforced local-only privacy rule — routing to the store README for detail per the established pattern; the Maintainer Checks table gained a store-touching-changes row naming the store suites and the unmodified PRD 32 baselines, and the Future Coverage gate narrowed from Phases 4 and 5 to Phase 5 plus the W18 R7/R11 consumers. User-guide coverage was `update-existing` with a deliberate partial landing: Phase 4 made the store user-visible for the first time through the uninstall disposition report, so [the lifecycle guide](../../library/user/cli-lifecycle-managing-installations.md) gained a subsection under Uninstall explaining what the report means — only this project's entries are pruned, the store itself is never deleted by repo-level uninstall, last-project runs name where the store can be safely deleted by hand, backups are unaffected, and the recorded project paths never leave the machine — while store inspection, the `setup remove` name, and the machine-footprint removal command stay gated in Future Coverage on W18 R11 only, since those are the actual command surfaces. PRD coverage was `risk-register-update` because the phase implemented existing PRD 38 requirements without changing the active requirement surface: in [the open questions and risk register](../../../prd/03-open-questions-and-risk-register.md), R-019's Decision cell records the P4 landing (seam-first lifecycle, disposition reporting, R-LIFE-3 verified at existing seams, PRD 32 byte-identity, privacy enforcement) with P5 and the W18 R7 R-TEST-5 consumption still open and its Follow-Up retargeted to runtime-state guidance and verification next; R-023's Decision cell records that the R-TEST-4 assertions it was pending closed — multi-project pruning proven and uninstall proven non-destructive with both protected backup roots surviving — and, with every literal to-close assertion now passing, the status call is that R-023 stays Open because the P3-recorded close bar explicitly includes the P5 verification pass re-proving the guards end to end, stated explicitly in the cell so the P5 session can close it with recorded evidence. The R-LIFE-1 wording question ("removed or the user is prompted" versus the implemented prune-and-inform plus deferred-prompt seam) was decided as not-yet-full-satisfaction that requires no PRD 38 edit: the requirement text stands unchanged, PRD 38's lineage note already assigns the self-management commands to PRD 39, and the carry-forward is recorded in the register instead — R-019 states the remove-or-prompt choice completes when W18 R11's tool-level `uninstall` calls `removeGlobalStore`, and R-024's Follow-Up (the W18 R11 owner) now carries the explicit instruction to call that seam and own the prompt. Headings, item numbers, and statuses in the register are unchanged. Manual-test/UAT coverage is deferred until wave completion per user instruction; the natural UAT is uninstalling one of two registered projects and confirming the disposition line reports the store kept for the other, then uninstalling the last project and confirming the report names the store location as safely deletable while `.make-docs/backup/` and root `.backup/` survive.

Validation: jdocmunch was reindexed over the docs tree, `.make-docs/scripts/check_path_hygiene.py` reports zero errors, every relative link added this session resolves, and `git diff --check` is clean. No template-owned files were touched (the template runtime-state guidance is Phase 5's deliverable), the uncommitted W18 R10 P4 code changes under `packages/cli/` were left as-is for the orchestrator's commit, and the concurrent W18 R6 P5 files (`packages/cli/tests/**`, `packages/cli/src/playbook/**`, `docs/work/2026-07-01-w18-r6-*`) were left untouched.
