# make-docs Evolution Direction

Supplemental reference notes preserving the forward direction for make-docs
beyond the current wave. This is seed material, not a contract or a commitment;
each item becomes authoritative only when it lands in a design, plan, PRD, and
work backlog. Risks and open questions for these items are tracked in
`docs/prd/03-open-questions-and-risk-register.md`.

## Documentation Restructure

- Move contents of `docs/assets/**` (contracts, references, templates, and the deterministic logic) into the in-project tool directory.
- Split that tool directory into a **system** tier (shipped, canonical) and a **custom** tier (adopter overlay) for contracts, references, templates, and scripts.
- Move `docs/assets/guides/` under a new `docs/library/`, and add `docs/library/playbooks/` so role-specific guides are separated from procedural playbooks.

See [evolution-direction-structure.md](evolution-direction-structure.md) for a detailed breakdown of the proposed structure.

## CLI Enhancements

### No Scripts / Thin Scripts (Move logic into the CLI)

Move all deterministic logic out of standalone scripts and into the CLI. Add an
MCP endpoint to the CLI, plus a skill that guides agents on using the CLI for
adopters who do not want to run the MCP server. Skills that currently rely on
standalone scripts should source that logic from the CLI instead.

Scripts will still exist under `.make-docs/scripts/`, but they will be segregated into `system/` and `custom/` subdirectories, and all `system/` scripts will be thin wrappers around CLI commands (which should help agents understand and use the CLI more effectively).

### Separation of Concerns

Currently, the CLI behaves as an installer/maintainer for make-docs.  However, it is intended to evolve into a standalone CLI tool that can be used by any agent, not just make-docs maintainers, with a focus on agent-friendly CLI usage and documentation, and an MCP server for agent interaction.  There is still a need for an installer, though, and so we have decided to split this functionality into two separate tools: a standalone CLI and an installer/maintainer.

The functionality of the installer/maintainer will largely be what it is today, though with necessary improvements to the interactive installers/updaters/etc., to reflect the changes to how make-docs works and is installed; it will also be one entry point for installing the standalone CLI.  However, it also needs significant improvements so that it can build as small and as lightweight as possible, and optionally be used without installing ANY dependencies (especially as an `npx` script that can be used without any local installation at all).

## Docs Metadata

All docs generated by make-docs should carry metadata in YAML frontmatter.

## Personas

- Persona primitives: **agent**, **maintainer**, **user**. Default personas
  derived from them: **Agent**, **Developer**, **User**. Adopters may add custom
  personas, each declaring its slug, label, description, and primitive.
- Persona attaches in two places: the directory
  (`docs/library/<guides|playbooks>/<persona>/`) and a `persona:` field in the
  YAML frontmatter of every persona-based doc. The frontmatter field is the
  canonical machine-readable target that the coverage-pass persona axis maps
  onto.

## Configuration and Conventions

- A config file in the tool directory lets adopters customize behavior.
- Adopters can redefine structural vocabulary (the equivalents of designs,
  plans, prd, work), coordinates (the equivalents of wave/revision/phase), and
  file-prefix style (slug-date vs version-number).
- **Overlay principle:** the customization layer renames *presentation* —
  user-visible vocabulary and generated text — never *structure*. Repo paths,
  frontmatter field names, skill names, and contract names stay canonical,
  because those are the contract users build automation against.

## Skills and Plugins Installation

Install shared agentic artifacts (skills, plugins, MCP servers) once in a single
location and create per-harness symlinks, instead of duplicating content across
each agent directory. The redirection must work across Linux, macOS, and
Windows.

### Adversarial Reviews

We should add "adversarial reviews" to skills like the Decompose Codebase skill, especially for "chunks" of analyzed parts of the codebase/system (such as PRDs, etc.).

## Plugins

- make-docs will support harness plugins (e.g., Claude Code and Codex), managed
  and installed by the CLI, opt-in like skills.
- Pre-built, domain/intent-centric bundles make the workflow push-button for
  different roles — for example a development bundle, a product-management
  bundle (requirements -> design -> plan -> PRD), or a writing/documentation
  bundle.
- A **Run Playbook** plugin always ships: it executes an arbitrary
  user-authored playbook, turning a repeatable process into a named "agent"
  with no code written.
- Plugins are the sanctioned entry point for non-maintainers, guarding against
  direct edits that could corrupt the doc set. They must respect the
  customization/mapping configuration.

## Playbooks vs Plugins (the boundary)

- **Playbook = content.** A persona-scoped, repeatable *process definition*
  (an artifact). It describes a workflow and does nothing on its own.
- **Plugin = invocation.** A harness entry point (slash command) that *drives*
  a process. It wraps either a built-in workflow or the generic Run Playbook
  executor.
- They do not overlap: a playbook with no plugin is still runnable by hand; a
  plugin with no user playbook still wraps a built-in process; the Run Playbook
  plugin is the seam between them.
