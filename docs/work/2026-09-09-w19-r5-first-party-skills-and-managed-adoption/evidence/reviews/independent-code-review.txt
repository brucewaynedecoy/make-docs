## Findings and fixes

1. **Recovery could fail after a native directory became a link.** The Store worker first reported and reproduced this case. I reviewed the failure path and the fix. Recovery now treats a removed child as absent only when a later saved parent state matches the disk. It does not allow arbitrary link parents. The exact tests `can resume an existing native directory after its final link exists but before commit`, `can rollback an existing native directory after its final link exists but before commit`, and `resumes a saved copy fallback after removing the reviewed native tree` pass.

2. **A removed native tool path could prevent final commit.** The saved link map must retain old link targets for rollback. The final check had required every entry in that map to remain installed. I reported the tool-change case; the worker's scope-change test also caught it. The check now permits an unowned retired path only when its saved final step and actual disk state are both missing. `reviews and completes a same-Skill scope and tool change` passes.

3. **Normal setup could adopt exact existing bytes without review.** An unowned file or copy could be marked as unchanged and then gain ownership when another missing file caused an apply. I reported this mixed case. The planner now treats existing unowned Skill roots as conflicts and directs the user to reviewed adoption. Both `does not implicitly adopt exact unowned bytes during normal skills with missing files` and the corresponding `normal setup` case pass.

4. **The profile ID did not include the new Skill tool choice.** I reported the missing field. The profile hash now includes the saved native Skill tool set. `uses different profile IDs for different saved native Skill tools` passes. `keeps Codex-only Skill selection on later plain sync in a two-router project` also passes. Explicit Skill tools stay separate from project router tools during full reconfigure; `setup skills` changes the Skill tool choice.

## Late Store review after the full-suite failure

The first full suite found an uninstall regression. A pending uninstall stores a JSON `null` final ledger. The new path-claim reader had treated that value as an object. The fixed reader checks the parsed value before reading its files. Recovery also uses an empty file set for a null final ledger. Saved file steps still reserve their paths. I requested explicit pending-uninstall resume and rollback cases and reviewed the final code.

The per-write conflict check now queries only pending operations from other checkouts. It reads their saved file steps and intended ledger paths, then uses the same canonical path and ancestor overlap checks. It does not cache the result or skip a later guarded write. The full ownership query remains in the adoption review. This change removes the repeated scan of committed ledgers without removing pending reservations or owner review.
