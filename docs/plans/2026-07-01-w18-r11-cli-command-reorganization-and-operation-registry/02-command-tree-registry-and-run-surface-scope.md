# Phase 2: Command Tree, Registry, and Run Surface Scope

## Scope

Settle the implementation scope the delta backlog must encode, grounded in the design's D0–D10 decisions, so backlog generation is transcription rather than re-derivation. This phase writes no repository files; it fixes the decision boundaries the backlog phases carry.

## Decision Areas

- Scope and preserved decisions (D0, D1): this change owns exactly the top-level command structure, bare-command behavior, tool self-management, the operation registry and shared core, the `run` surface, and migration and sequencing (R-SCOPE-1 exclusions listed below). The preserved decisions are unchanged per R-KEEP-1: TypeScript runtime authority with Rust shelved, remote execution through `npx`, `pnpm dlx`, and `bunx` as the primary posture, the installer-first no-command posture, MCP delegation to the same deterministic operation contract with identical reads, config interpretation, provenance, audit, dry-run, and write permissions, modular operation domains behind thin dispatchers, and project `.make-docs/config.yaml` as presentation overlay never routing authority.
- Top-level structure (D2): five top-level commands organized as self, project, run, and serve — `setup` with `setup reconfigure`, `setup skills`, `setup backup`, and `setup remove`; `run`; `mcp`; `update`; `uninstall` (R-TOP-1). `setup remove` replaces the project-level `uninstall`, freeing the `uninstall` name for machine-level removal (R-TOP-2). Multi-operation families under `run` use a subtree under a domain object mapping one-to-one to registry identifiers; standalone utilities are flat (R-TOP-3).
- Bare command (D3): bare `make-docs` is context-aware — with no install detected it starts a guided `setup` that asks before writing, and with an install present it shows status and help and never auto-syncs, preserving the installer-first posture without a forced command-router (R-BARE-1).
- Tool self-management (D4): `uninstall` removes the machine-level footprint — the global store at `~/.make-docs/` and the installed binary when present — reports no-binary for remote-execution users, is a hard cutover, and confirms before removing (R-SELF-1); `update` is a detect-and-delegate wrapper over the install manager that reports nothing-persistent for remote execution and applies global-store schema migrations (R-SELF-2); neither command guesses and then executes a destructive global change — on ambiguity it prints the exact command and the affected store path (R-SELF-3).
- Registry and shared core (D5): a single operation registry is the source of truth with stable, append-only, lowercase dot-separated `domain.verb` or `domain.object.verb` identifiers with hyphenated multiword segments (R-REG-1); the CLI `run` tree and the MCP tool list are generated from or conformance-checked against the registry (R-REG-2); deterministic logic lives in a shared operation core of modular per-operation modules grouped by domain, never a monolith, where every operation is a stable identifier, typed input, typed output, mutation classification, and a handler taking input plus an injected execution context that enforces dry-run, write-permission, and approval uniformly, with surfaces adapting inputs and outputs and containing no operation logic and presentation belonging to the surface (R-CORE-1); dependencies are one-way — surfaces depend on the core, never the reverse, and no surface imports another surface (R-CORE-2); the three surfaces are the CLI `run` command, the MCP tools, and Playbook `operation:` steps, while `setup`, `mcp`, `update`, and `uninstall` are lifecycle commands that are not registry operations and no Playbook step may install, serve, update, or uninstall the tool (R-SURF-1).
- The `run` surface after pruning (D6): `run` exposes only registry operations — `run playbook` with catalog, resolve, capabilities, start, invoke, status, next, advance, gate, resume, and close; `run package` with plan, surface-resolve, and write; and exactly two retained work operations, a work-item identity resolver and the work-execution evidence record and read keyed to the global-store project-state model (R-RUN-1). The pruned derivation, judgment, and generation operations — wave-status, work-phase-state, phase-plan, the phase-gate decision, scope-guard, and the closeout probe, validate, and history logic — must not be carried into the new surface; they are rebuilt as Playbooks per the inventory disposition (R-RUN-2).
- Migration and upgrade safety (D7): no back-compatibility aliases (R-MIG-1); `update`, `setup`, and `setup reconfigure` detect pre-v2 configuration fingerprints and present a warning itemizing breaking changes with a backup-and-install-latest (recommended) or cancel choice (R-MIG-2); MCP tool names are derived from registry identifiers so MCP renames follow the same registry as the CLI (R-MIG-3).
- Sequencing (D8): establish the core, the registry, and the reorganized tree first and move all retained operation logic behind the registry in the same wave to avoid a half-migrated state (R-SEQ-1); internal modularization of the messiest retained logic may be a tracked follow-up, and removal of the pruned operations is tracked by the inventory disposition and must not block the reorganization (R-SEQ-2); only logic passing the NORTHSTAR filter — a fact-of-record or a fiddly, genuinely reused canonical-identity or parse primitive — is retained as a registry operation, and derivation-heavy behavior's destination is a Playbook (R-SEQ-3).
- Fixed versus open (D9): the non-substitutable decisions are the five-command structure and self/project/run/serve organization, context-aware bare, machine-footprint `uninstall` with hard cutover and remote-execution-honest self-management, the registry as single source with derived surfaces, the shared modular core with the uniform contract and one-way dependencies, the registry-operations-only pruned `run` surface, and no aliases plus pre-v2 detection; the implementer freedoms are the exact names of the two retained work operations, the pre-v2 fingerprint set and warning copy, the install-manager detection matrix, and the internal module layout of the operation core — the backlog must treat the former as acceptance criteria and leave the latter open.
- Verification (D10): tests assert CLI/MCP registry parity with no operation present in one surface and absent in the other (R-TEST-1), operation invocation through the core without the CLI parser or MCP transport (R-TEST-2), that `run` exposes no `setup`, `mcp`, `update`, or `uninstall` operation and a Playbook step cannot invoke tool lifecycle (R-TEST-3), and the pre-v2 warning-and-choice flow, `uninstall` confirmation without repository-content deletion, and the pruned operations' absence from the `run` surface (R-TEST-4).

## Cross-Design Sequencing

- Same-wave rule per R-SEQ-1: the operation core, the registry, and the reorganized command tree land first, with all retained operation logic behind the registry in the same wave, so the backlog orders the registry and core before the tree consumers and never leaves some operations registry-backed while others are hand-wired.
- Consumes W18 R10: the two retained work operations record and read evidence through the global store's unified project-state model per [PRD 38](../../prd/38-revise-global-store-and-project-state.md), so their implementation is gated on the store, its concurrency model, and the stable project identifier landing per the W18 R10 backlog phases.
- Consumes W18 R7: the `run playbook` progression verbs and their semantics are owned by [PRD 35](../../prd/35-revise-run-playbook-state-machine.md); this lineage fixes only their command surface and registry identifiers.
- Documentation consequence: any template-owned instruction router, guide, or README naming old command spellings such as `operations` or the project-level `uninstall` is updated upstream in `packages/docs/template/` first and then dogfooded per the maintainer dogfooding rule; this is backlog implementation work, not part of this documentation pass.

## Out of Scope per R-SCOPE-1

The backlog must not redefine the internal logic of the operations or the pruning removals (tracked by [migrated-operations-inventory.md](../../assets/artifacts/migrated-operations-inventory.md)), the Playbook model, runner, packaging, and conformance (owned by the W18 R6 through R9 lineages), the global store schema and project-state model (owned by [PRD 38](../../prd/38-revise-global-store-and-project-state.md)), or the CLI/MCP boundary and TypeScript runtime authority (preserved from the predecessor designs and not reopened).
