# Phase 2: Compiler, Capability Model, and Adapter Scope

## Scope

Settle the implementation-shaping decisions the delta backlog must encode so no implementing agent has to re-derive them: what the compiler emits and through which plumbing, where the deterministic-versus-agent-assisted line sits, how each dependency kind materializes, what the capability descriptor declares, how each adapter's verified contract reads, when packaging fails closed, and where the deterministic seams to other designs sit. This phase produces decisions recorded in the backlog phases, not code.

## Inputs

- Design decisions D0 (scope and boundaries), D1 (preserved prior decisions), D2 (packaging is a compiler), D3 (deterministic and agent-assisted generation), D4 (dependency materialization), D5 (harness capability and distributable model), D6 (verified adapter contracts), D7 (marketplace and registration seam), D8 (provenance, lifecycle, and support), D9 (non-negotiables versus deliberately open choices), and D10 (verification and testability).
- [Playbook Architecture and Design](../../assets/artifacts/playbook-architecture.md) Sections 6–8 as source material; the design is the authority where they differ.
- [PRD 34](../../prd/34-revise-playbook-contract-and-model.md) for the Playbook model, rich steps, typed dependency registry, and activation content the compiler consumes, and [PRD 28](../../prd/28-revise-shared-agentics-installation-harness-redirection.md) for the exposure plumbing the compiler writes through unchanged.

## Outputs

- Compiler scope: the output writer produces a real, harness-native, multi-file distributable and never a Make Docs descriptor as the installable artifact (R-COMP-1); it reuses the exposure plumbing unchanged — canonical payload under the staging area, exposure mirror by symlink or copy-mirror, and manifest ownership records tracking both — so only the payload content changes (R-COMP-2); the distributable is a multi-file tree that is a function of the Playbook model and the target and can emit a `SKILL.md` per source Playbook, references, deterministic helper and dependency-check scripts, tool and dependency declarations, hooks from event-bound steps, the harness-native manifest, marketplace or registration files, lifecycle records, and conformance records (R-COMP-3).
- Generation scope: generation is two-tier with the boundary recorded in field provenance — schema-owned fields (file paths, manifest structure, dependency checks, provenance, digests) are deterministic, and semantic fields (skill descriptions and triggers, bundle grouping, harness-facing prose) are review-gated agent-assisted proposals (R-GEN-1); the compiler fails closed before any write when unresolved semantic decisions, ownership conflicts, missing dependencies, unsupported surfaces, or missing conformance evidence require review (R-GEN-2).
- Materialization scope: the dependency kind from the Playbook dependency registry determines materialization — `cli`/`package-manager` as check scripts plus human instructions with Make Docs `cli` dependencies referencing operation identifiers rather than command strings, `skill`/`plugin` as harness-native manifest references or explicit degradation, `mcp`/`external-service` as metadata plus a runtime availability check, `reference` as copy/extract where redistribution is allowed and link otherwise, and `playbook` as an additional skill when bundled or a reference when not (R-DEPMAT-1).
- Capability scope: the packaging-time and run-time capability questions share one harness registry, with the run-time question owned by the W18 R7 runner (R-CAP-1); each harness has a capability descriptor declaring identifier, supported agentic primitives, native container and its file layout, lifecycle event map, exposure modes, registration model, and preconditions, as the single home of harness-specific packaging knowledge (R-CAP-2); authoring granularity is one Playbook to one skill while distribution granularity is the distributable, with `plugin` interpreted as the richest native container and `skills-bundle` as the portable agents-standard form (R-CAP-3); the adapter selects the richest supported container, maps implied agentics onto supported primitives, and declares degradation or an unsupported-surface stop, never silently (R-CAP-4); event-bound steps compile to declared hook points or degrade/fail closed per R-CAP-4 (R-CAP-5).
- Adapter scope: every adapter's paths, manifest shapes, and registration steps are verified against the real harness with a verification reference and status, and an unverified adapter may produce only export-only or provisional output and carries no support claim (R-ADAPT-1); the Codex adapter follows the verified contract — a plugin is a folder containing `.codex-plugin/plugin.json` registered through a marketplace entry such as `.agents/plugins/marketplace.json` or a configured marketplace source, and a skills bundle uses direct `.agents/skills/{id}/SKILL.md` discovery — superseding the assumed `.agents/plugins/{packageId}` path and descriptor payload (R-ADAPT-2); the Claude Code adapter lowers to `.claude/plugins/{id}/plugin.json` and `.claude/skills/{id}/SKILL.md` or agents-standard for the portable profile, lowers event-bound steps to its hook points, and stays provisional until reviewed against the actual contract (R-ADAPT-3); the Pi adapter's richest container is an extension bundled with skills, with event-bound steps degrading or failing closed because Pi lacks hooks (R-ADAPT-4); unknown harness, unsupported output kind, unsupported surface, or unhonorable scope fails closed before any write, and a fixture adapter exercises the unsupported path (R-ADAPT-5).
- Marketplace scope: registration and marketplace files are generated into the distributable but a user's global marketplace is never auto-mutated without explicit global scope and approval — generate but do not install is the default (R-MKT-1); a config-gated policy seam in the global store may later opt into auto-registration, additive and off by default, with the store owned by the Runtime and Global Store lineage (R-MKT-2).
- Provenance scope: every generated artifact carries source ref and digest, package profile, adapter id, output kind, generated files, ownership status, and support status (R-PROV-1); backup and uninstall remove only Make Docs-owned generated outputs without orphaning empty managed directories or deleting user-authored files, proven by a conformance scenario (R-PROV-2); support claims stay provisional until conformance evidence exists and bind to the exact scenario/harness/surface/scope/output-kind/model-or-provider/runtime tuple (R-PROV-3).
- Boundary confirmations: the Playbook schema, workflow contract, step model, dependency registry, model, parser, and validator; the run-state machine; conformance and the tuple registry; and the operation registry, CLI tree, and global store are owned elsewhere and must not be redefined (R-SCOPE-1); every W18 R5 decision listed in D1 — the reviewed pipeline, deterministic rails, plan-drafting-only agent assistance, the target model, the adapter registry, the harness-neutral planner and surface resolver, generated-output provenance, bundles not mapping one-to-one to plugins, and tuple-bound support — is preserved unchanged (R-KEEP-1).
- Implementer freedoms preserved per D9: the internal compiler structure given the required inventory and generation split, the exact organization of generated files within the harness's layout constraints, the prompt wording for agent-assisted proposals, and the internal structure of each adapter module given a verified declared contract stay open in the backlog and are not over-specified.

## Validation

- Every backlog decision traces to a D-section and R-* requirement, and everything D9 fixes as non-negotiable appears as an acceptance criterion rather than an open choice.
- No backlog task redefines the Playbook model, the run-state machine, conformance or the tuple registry, the operation registry, or the global store, and the conformance-evidence dependency is stated wherever support-claim or recognition work is tasked.
